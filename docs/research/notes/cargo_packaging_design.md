- Quotes marked "(raw)" were read verbatim from the repository file with `curl`. Quotes without that mark came through a summarising fetch tool and should be treated as close paraphrase unless the wording is obviously a direct quotation of the page.
- Latest stable toolchain at time of writing: Rust 1.99.0, released 2026-10-01 — [rust-lang/rust releases](https://api.github.com/repos/rust-lang/rust/releases?per_page=3). ## 1. Hard limits: features per crate, crate size, dependencies

### Takeaway
crates.io caps a crate at 300 features (since 2023-10-16), 500 dependencies, and a 10 MB compressed `.crate` file; the feature and size caps have per-crate overrides granted by email, the dependency cap has no per-crate override in the code. "One crate, one feature per integration" therefore stops at fewer than 300 integrations unless the crates.io team grants an exemption, and an umbrella facade crate hits the same 300-feature and 500-dependency ceilings.

### Cited Findings
- Current default publish limits in crates.io source (raw, `src/config/publish_limits.rs`, main branch, read 2026-10-08): `upload_size: 10 * 1024 * 1024 // 10 MB`, `unpack_size: 512 * 1024 * 1024 // 512 MB`, `DEFAULT_TARBALL_ENTRIES: usize = 30_000`, `metadata_file_size: 1024 * 1024 // 1 MB`, `dependencies: 500`, `features: 300` — [rust-lang/crates.io publish_limits.rs](https://github.com/rust-lang/crates.io/blob/main/src/config/publish_limits.rs)
- The feature limit is two limits: total features in the crate, and the number of entries any single feature may enable. Error text (raw): "crates.io only allows a maximum number of {max_features} features or dependencies that another feature can enable, but the \"{key}\" feature of your crate is enabling {num_features} features or dependencies." — [rust-lang/crates.io publish.rs](https://github.com/rust-lang/crates.io/blob/main/src/controllers/krate/publish.rs)
- Exemption route (raw error text): "If you have a use case that requires an increase of this limit, please send us an email to help@crates.io to discuss the details." The same wording is used for the 500-dependency limit — [rust-lang/crates.io publish.rs](https://github.com/rust-lang/crates.io/blob/main/src/controllers/krate/publish.rs)
- Per-crate overrides are stored as nullable columns `max_features` (`Nullable<Int2>`) and `max_upload_size` (`Nullable<Int4>`) on the `crates` table; publish code reads `existing_crate.max_features` and `existing_crate.max_upload_size()` first and falls back to the defaults. The dependency limit reads only `ctx.config.publish_limits.dependencies` (no per-crate column) — [crates.io schema.rs](https://github.com/rust-lang/crates.io/blob/main/crates/crates_io_database/src/schema.rs); [publish.rs](https://github.com/rust-lang/crates.io/blob/main/src/controllers/krate/publish.rs)
- Origin of the 300 limit: "on 2023-10-16 the crates.io team deployed a change limiting the number of features a crate can have to 300". The trigger was an unnamed crate that "provides SVG icons for Rust-based web applications" and "uses one feature per icon", with "almost 23,000" features; its API response had "broken the 20 MB mark" (which broke a shields.io badge) and "With 9 published versions it already contains 11 MB of data" in the index. The limit is described as holding "for now, or at least until we have found solutions". Crates with legitimate need were "granted ... appropriate exceptions"; the post does not name them — [Rust Blog, "A tale of broken badges and 23,000 features", 2023-10-26](https://blog.rust-lang.org/2023/10/26/broken-badges-and-23k-keywords/)
- Cargo Book restates it: "New crates or versions published on crates.io are now limited to a maximum of 300 features. Exceptions are granted on a case-by-case basis." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- Size limit in the Cargo Book: "crates.io currently has a 10MB size limit on the `.crate` file." — [Cargo Book, Publishing](https://doc.rust-lang.org/cargo/reference/publishing.html)
- Crates currently above 300 features (registry snapshot 2026-10-08), so each must hold an override: `web-sys` 0.3.106 (2026-09-25) 1,727 features; `embassy-stm32` 0.6.0 (2026-03-20) 1,576 features; `windows` 0.62.2 (2025-10-06) 674 features — [web-sys](https://crates.io/api/v1/crates/web-sys), [embassy-stm32](https://crates.io/api/v1/crates/embassy-stm32), [windows](https://crates.io/api/v1/crates/windows)
- `windows-rs` exemption confirmed in the project's own tracker: "The current windows-rs crates are exempt and crates.io will consider other legitimate exemptions too." (issue opened 2023-10-30 by Chris Denton) — [microsoft/windows-rs#2693](https://github.com/microsoft/windows-rs/issues/2693)
- Size override in practice: `windows` 0.48.0 (2023-03-31) is 11,864,177 bytes and 0.52.0 (2023-11-15) is 11,843,715 bytes, both above the 10 MB default; the current 0.62.2 is 9,360,572 bytes — [windows 0.48.0](https://crates.io/api/v1/crates/windows/0.48.0), [windows 0.52.0](https://crates.io/api/v1/crates/windows/0.52.0), [windows](https://crates.io/api/v1/crates/windows)
- `windows-sys` is under the limit and has been since before it existed: 278 features at 0.48.0 (2023-03-31), 247 at 0.61.2 (2025-10-06) — [windows-sys 0.48.0](https://crates.io/api/v1/crates/windows-sys/0.48.0), [windows-sys](https://crates.io/api/v1/crates/windows-sys)
- docs.rs build limits: "Available RAM: 6.4 GB", "Maximum rustdoc execution time: 15m", "Network access: blocked", "Maximum number of build targets: 10"; increases are requested by opening an issue, and "Any crate that requests a time extension will be limited to one target." — [docs.rs, About builds](https://docs.rs/about/builds)

### Inferences
- A single feature that enables everything (`full`, `all-integrations`) is itself capped at 300 entries, so even a facade with fewer than 300 features cannot offer a flat "everything" feature beyond that; it needs nested group features (for example `all-crm`, `all-chat`), each under 300 entries.
- An umbrella facade with one optional dependency per integration is bounded by whichever is lower: 300 features or 500 dependencies (the dependency count includes dev, build and target-specific dependencies per `convert_dependencies`). Thousands of integrations cannot sit behind one facade crate without an exemption on features and a code change on crates.io for dependencies.
- Every published version repeats the full feature map in the registry index, so feature count multiplies by release count. With frequent releases (integration libraries release often), this is the cost crates.io was protecting against (11 MB after 9 versions in the triggering case).
- The exemptions granted so far are all generated bindings to a fixed external surface (Web IDL, Windows metadata, STM32 chip families). A hand-written SaaS-connector crate asking for an exemption has no precedent I could find.

### Gaps
- The blog post and crates.io code do not publish the list of exempt crates or their per-crate ceilings; I inferred `web-sys` and `embassy-stm32` exemptions from their feature counts only.
- Whether crates.io has ever raised the 500-dependency limit for any crate is unknown; the code path has no per-crate override, and I found no announcement.
- I did not find a Cargo-side (client) limit on feature count; the limits above are registry policy. Alternative registries are not bound by them.
- I did not retrieve the introduction date of the 500-dependency limit.

## 2. What large projects did, with numbers

### Takeaway
Projects with hundreds of backends generated from machine-readable specs (AWS, Google, Azure) use one crate per service with no umbrella crate; projects that put everything behind features in one crate (web-sys, windows, embassy-stm32) are generated bindings holding crates.io exemptions; and the closest analogue to a hand-written multi-backend library, Apache OpenDAL, moved from one crate with `services-*` features to one crate per service plus a facade during 2025-11 to 2026-05.

### Cited Findings

**AWS SDK for Rust (one crate per service, no facade)**
- 467 directories under `sdk/` in `awslabs/aws-sdk-rust` on 2026-10-08, of which 30 are `aws-*` runtime/support crates (`aws-config`, `aws-sigv4`, `aws-smithy-*`, `aws-types`, ...), leaving 437 service crates — [aws-sdk-rust sdk/ listing](https://api.github.com/repos/awslabs/aws-sdk-rust/contents/sdk)
- Rationale (raw, smithy-rs design FAQ, "Why is there one crate per service?"): "Although it's possible to use cargo features to conditionally compile individual services, we decided that this added significant complexity to the generated code. In Rust the "unit of compilation" is a Crate, so by using smaller crates we can get better compilation parallelism. Furthermore, ecosystem services like `docs.rs` have an upper limit on the maximum amount of time required to build an individual crate—if we packaged the entire SDK as a single crate, we would quickly exceed this limit." — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)
- Versioning rationale (raw, same FAQ): "New updates will be pushed for _some_ AWS service nearly every day. Maintaining separate crates allows us to only increment versions for the relevant pieces that change." — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)
- Even a single service crate approaches the size cap: `aws-sdk-ec2` 1.267.0 (2026-10-01) is 7,709,190 bytes compressed with 331 published versions; `aws-sdk-s3` 1.152.0 is 1,822,172 bytes with 204 versions — [aws-sdk-ec2](https://crates.io/api/v1/crates/aws-sdk-ec2), [aws-sdk-s3](https://crates.io/api/v1/crates/aws-sdk-s3)

**Google**
- `google-apis-rs` (Byron): "Each google API resides in it's own crate"; generated from the Google discovery service; 660 entries under `gen/` on 2026-10-08. The project is in "Maintenance Mode": "No new features will be implemented", with "occasional updates of all crates ... probably no more than twice a year" — [google-apis-rs README](https://github.com/Byron/google-apis-rs/blob/main/README.md), [gen/ listing](https://api.github.com/repos/Byron/google-apis-rs/contents/gen)
- `google-cloud-rust` (official): crates are versioned independently, for example `google-cloud-storage` 1.20.0 (2026-09-30), `google-cloud-secretmanager-v1` 1.14.0 (2026-09-24), `google-cloud-gax` 1.15.0 (2026-09-24); the root workspace lists 42 explicit members and `src/generated/` has 32 top-level product-family directories — [google-cloud-storage](https://crates.io/api/v1/crates/google-cloud-storage), [google-cloud-secretmanager-v1](https://crates.io/api/v1/crates/google-cloud-secretmanager-v1), [google-cloud-rust Cargo.toml](https://github.com/googleapis/google-cloud-rust/blob/main/Cargo.toml)

**Azure**
- "Each supported Azure service is its own separate crate." The repo is the successor to the community `azure_sdk*` crates, which "should be considered fully deprecated". `sdk/` holds 8 directories on 2026-10-08: canary, core, cosmos, eventhubs, identity, keyvault, servicebus, storage — [azure-sdk-for-rust README](https://github.com/Azure/azure-sdk-for-rust/blob/main/README.md), [sdk/ listing](https://api.github.com/repos/Azure/azure-sdk-for-rust/contents/sdk)
- Independent versions: `azure_core` 1.2.0-beta.1 (2026-09-05), `azure_storage_blob` 1.1.0 (2026-09-08), `azure_identity` 1.1.0-beta.1 — [azure_core](https://crates.io/api/v1/crates/azure_core), [azure_storage_blob](https://crates.io/api/v1/crates/azure_storage_blob)

**windows / windows-sys / web-sys / embassy-stm32 (many features in one crate)**
- `web-sys` rationale (raw): "To keep `web-sys` building as fast as possible, there is a cargo feature for every type defined in `web-sys`. To access that type, you must enable its feature. To access a method, you must enable the feature for its `self` type and the features for each of its argument types." — [wasm-bindgen guide, Cargo features in web-sys](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/guide/src/web-sys/cargo-features.md)
- `web-sys` feature growth: 1,566 (0.3.64, 2023-06-12) to 1,727 (0.3.106, 2026-09-25) — [web-sys 0.3.64](https://crates.io/api/v1/crates/web-sys/0.3.64), [web-sys](https://crates.io/api/v1/crates/web-sys)
- `windows` feature count held roughly flat at 667 (0.48.0, 2023-03) / 682 (0.52.0) / 691 (0.58.0) / 695 (0.61.3) / 674 (0.62.2). Maintainer Kenny Kerr on why it cannot shrink (raw, 2023-10-31): "The features are based on namespaces including nested namespaces. ... While we could refactor some of the Win32 namespaces, WinRT namespaces are fixed. Obviously, the main drawback of collapsing these further is that it would cause more code to be included for compilation and that's undesirable." The issue was closed with "reducing the feature count by only a little would not be worth the trouble and a more substantial reduction would be undesirable" — [microsoft/windows-rs#2693](https://github.com/microsoft/windows-rs/issues/2693)
- `embassy-stm32`: 1,362 features (0.1.0, 2024-01-11), 1,466 (0.2.0, 2025-01-10), 1,576 (0.6.0, 2026-03-20), published after the limit existed — [embassy-stm32 0.1.0](https://crates.io/api/v1/crates/embassy-stm32/0.1.0), [embassy-stm32](https://crates.io/api/v1/crates/embassy-stm32)

**Apache OpenDAL (moved from features-in-one-crate to crate-per-service plus facade)**
- Before the split, `opendal` carried 61 to 67 `services-*` features in one crate: 0.45.0 (2024-02-05) 83 features / 61 services; 0.50.0 (2024-09-18) 85 / 67; 0.55.0 (2025-11-20) 83 / 63, crate size 881,564 bytes — [opendal 0.45.0](https://crates.io/api/v1/crates/opendal/0.45.0), [opendal 0.50.0](https://crates.io/api/v1/crates/opendal/0.50.0), [opendal 0.55.0](https://crates.io/api/v1/crates/opendal/0.55.0)
- RFC 6828 (start date 2025-11-27): `opendal-core` owns types, raw traits and critical layers; each backend lives in `opendal-service-{backend}`; non-critical layers move to `opendal-layer-{name}`; a facade `opendal` re-exports and registers services. Stated motivation: users build only the services and layers they need; "service delivery and versioning become independent"; correctness-critical layers stay in core; readiness for third-party services. Stated drawbacks: more release coordination across crates; users who bypass the facade must enable services/layers manually; "Dependency solver performance may degrade with numerous optional dependencies". A single consolidated `opendal-layers` crate was rejected to keep granular feature control — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)
- Tracking issue opened 2025-11-27, now closed; it listed 60+ services and 17 layers to extract, keeping feature flags and behavior tests — [apache/opendal#6829](https://github.com/apache/opendal/issues/6829)
- After the split (registry snapshot): `opendal` 0.59.4 (2026-10-05) has 104 features = 68 `services-*` + 24 `layers-*` + 12 others, and each service feature is a pure dependency switch, for example `services-s3 = ["dep:opendal-service-s3"]`, `layers-logging = ["dep:opendal-layer-logging"]`. The facade shrank to 191,211 bytes at 0.56.0 (2026-05-01). `opendal-core` has 6 features — [opendal 0.59.4](https://crates.io/api/v1/crates/opendal/0.59.4), [opendal 0.56.0](https://crates.io/api/v1/crates/opendal/0.56.0), [opendal-core](https://crates.io/api/v1/crates/opendal-core)
- Repo layout on 2026-10-08: 66 directories under `core/services` (one is the shared `azure-common`) and 25 under `core/layers` — [core/services](https://api.github.com/repos/apache/opendal/contents/core/services), [core/layers](https://api.github.com/repos/apache/opendal/contents/core/layers)
- The split crates are released in lockstep, not independently: `opendal-core`, `opendal-service-s3`, `opendal-service-github` and `opendal-layer-retry` are all 0.59.4, all updated 2026-10-05, each with exactly 10 published versions — [opendal-service-s3](https://crates.io/api/v1/crates/opendal-service-s3), [opendal-service-github](https://crates.io/api/v1/crates/opendal-service-github), [opendal-layer-retry](https://crates.io/api/v1/crates/opendal-layer-retry)

**Vector (per-component features in one binary crate)**
- Root `Cargo.toml` on master (2026-10-08) declares 268 features, of which 63 start with `sources-`, 58 with `sinks-`, 23 with `transforms-`; the file has 98 `optional = true` occurrences — [vector Cargo.toml](https://github.com/vectordotdev/vector/blob/master/Cargo.toml)
- Policy (raw): "When a new component (a source, transform, or sink) is added, it has to be put behind a feature flag with the corresponding name. This ensures that it is possible to customize Vector builds." and "If a dependency is required only by one or multiple components, but not by Vector's core, make it optional and add it to the list of dependencies of the features corresponding to these components" — [vector DEVELOPING.md](https://github.com/vectordotdev/vector/blob/master/docs/DEVELOPING.md)
- Compile-time pain and workaround (raw): "during development of a particular component it is useful to disable all other components to speed up compilation ... In case if the tests are already built and only the component file changed, it is around 4 times faster than rebuilding tests with all features." A dedicated `make check-component-features` target exists — [vector DEVELOPING.md](https://github.com/vectordotdev/vector/blob/master/docs/DEVELOPING.md)
- Early contributor report (2020-01-11): "on every tiny change that I make rls takes a significant amount of time (tens of seconds) to react. This happens because it spends a lot of time recompiling (or, more specifically, checking) the code." — [vectordotdev/vector#1514](https://github.com/vectordotdev/vector/issues/1514)

**sqlx, tokio, icu4x, bevy, tower-http, rig**

- `icu` 2.3.1 (2026-08-20) is a meta-crate with 8 features over component crates; `icu4x` has 18 directories under `components/` — [icu](https://crates.io/api/v1/crates/icu), [icu4x components/](https://api.github.com/repos/unicode-org/icu4x/contents/components)
- `bevy` 0.19.1 (2026-08-13) umbrella has 172 features; `tower-http` 0.7.1 (2026-08-31) has 35 — [bevy](https://crates.io/api/v1/crates/bevy), [tower-http](https://crates.io/api/v1/crates/tower-http)
- `rig`: 28 crates under `crates/` (`rig-core`, `rig-mongodb`, `rig-qdrant`, `rig-bedrock`, `rig-lancedb`, ...). `rig-core` 0.44.0 has 12 features, none of them per-provider (`audio`, `derive`, `epub`, `image`, `pdf`, `reqwest`, `rustls`, ...) — [rig crates/](https://api.github.com/repos/0xPlaygrounds/rig/contents/crates), [rig-core 0.44.0](https://crates.io/api/v1/crates/rig-core/0.44.0)

### Inferences
- No project I examined offers hundreds of hand-written integrations as features of one published crate. The two shapes that exist at 400+ scale are crate-per-service (AWS 437) and feature-per-item generated bindings with a registry exemption (web-sys 1,727; embassy-stm32 1,576; windows 674).
- OpenDAL's shipped result differs from its RFC text in two ways worth copying or avoiding: the RFC proposed renaming features to `service-s3` / `layer-logging`, but 0.59.4 still exposes `services-*` / `layers-*` (zero `service-` features), so they kept user-facing names stable; and the RFC cites independent versioning as a motivation while the crates are in fact published in lockstep.
- OpenDAL's facade at 104 features is one-third of the way to the 300 cap with 68 services; at its historical growth (61 services in 2024-02, 68 in 2026-10) it will not hit the cap, but a connector library targeting "hundreds to thousands" would.
- AWS deliberately has no umbrella crate; `aws-config` is shared configuration, not a re-export facade. That avoids the facade's 300-feature / 500-dependency ceiling entirely.
- Vector can carry 268 features because it is built as a binary from a git workspace; I did not verify whether the main crate is published to crates.io, where 268 would still be under the cap.
- `rig-core` having no per-provider features suggests model providers are compiled into core unconditionally while heavier stores live in companion crates; I did not open the source to confirm.

### Gaps
- No published before/after compile-time or dependency-count measurements for OpenDAL's split were found (the tracking issue has none; a GitHub search for "compile time" in the repo titles returned nothing).
- I could not obtain an exact crate count for `google-cloud-rust` (the workspace uses a mix of explicit members and generated trees) or confirm how many of the 660 `google-apis-rs` `gen/` entries are libraries versus CLI crates.
- I found no documented docs.rs build failure for `web-sys` or `windows` specifically; the docs.rs time limit is cited by AWS as a design reason, not as an observed failure of those crates.
- `icu4x` rationale for its meta-crate design was not retrieved; only structure and counts are sourced.

## 3. Compile time, binary size, CI cost and feature-combination tooling

### Takeaway
Published hard numbers are thin: the best primary data points are Vector's "around 4 times faster" single-component builds, smithy-rs's "23% slower" with serde derives, and a 95.8 s build of one AWS service crate; nobody appears to have published resolution-time or lockfile-size curves versus feature count. Exhaustive feature-combination testing is exponential, and the tools exist mainly to cap it.

### Cited Findings
- Vector: building and testing one component with `--no-default-features --features sinks-console` "is around 4 times faster than rebuilding tests with all features" — [vector DEVELOPING.md](https://github.com/vectordotdev/vector/blob/master/docs/DEVELOPING.md)
- smithy-rs: "When we last checked, adding `serde` derives made compilation 23% slower"; proc-macro dependencies (`proc-macro2`, `quote`, `syn`) are called "very expensive to compile" — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)
- AWS SDK issue "Compile time", opened 2021-06-15, still open with 51 comments: `aws-sdk-ec2` v0.0.8-alpha took 95.8 s versus `rusoto_ec2` v0.46.0 at 66.5 s under `cargo +nightly build -Z timings` (hardware not stated) — [awslabs/aws-sdk-rust#113](https://github.com/awslabs/aws-sdk-rust/issues/113)
- Crates as the parallelism unit: "In Rust the "unit of compilation" is a Crate, so by using smaller crates we can get better compilation parallelism." — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)
- OpenDAL's maintainers list as a drawback of the split: "Dependency solver performance may degrade with numerous optional dependencies" (no measurement given) — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)
- Registry-side cost of many features: one crate with ~23,000 features produced a 20 MB+ API response and 11 MB of index data across 9 versions — [Rust Blog 2023-10-26](https://blog.rust-lang.org/2023/10/26/broken-badges-and-23k-keywords/)
- Cargo's own guidance: "We encourage you to consider your strategy and tooling in regards to different feature combinations — Every project will have different requirements in conjunction with time, resources, and the cost-benefit of covering specific scenarios." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- `cargo-hack`: `--each-feature` ("Perform for each feature which includes default features and `--no-default-features` of the package"), `--feature-powerset`, `--depth` ("Specify a max number of simultaneous feature flags of `--feature-powerset`. If the number is set to 1, `--feature-powerset` is equivalent to `--each-feature`"), `--group-features`, `--mutually-exclusive-features`, `--exclude-features`, `--at-least-one-of`, and `--no-dev-deps` (workaround for dev-dependencies leaking features into normal builds) — [taiki-e/cargo-hack README](https://github.com/taiki-e/cargo-hack)
- `cargo-all-features`: runs build/check/test "with all feature flag combinations"; offers `skip_feature_sets`, `denylist`, `allowlist`, `max_combination_size` ("useful for reducing the number of combinations run for a crate with a large amount of features") and chunking (`--n-chunks 3 --chunks 1`) because "for large workspaces `check-all-features` and friends can take a very long time and produce a ton of artifacts" — [frewsxcv/cargo-all-features README](https://github.com/frewsxcv/cargo-all-features/blob/master/README.md)
- Workspace-level feature unification control is still unstable in Cargo: `-Z feature-unification` enables `resolver.feature-unification` with values `selected`, `workspace`, `package` (RFC 3692, tracking issue rust-lang/cargo#14774) — [Cargo Book, Unstable features (nightly)](https://doc.rust-lang.org/nightly/cargo/reference/unstable.html)

### Inferences
- A full powerset over N independent integration features is 2^N builds; at 68 features (OpenDAL's service count) that is unreachable, so the practical ceiling is `--each-feature` (N+2 builds) plus a handful of curated combinations. With one crate per integration, the same coverage is N ordinary crate builds that parallelise and cache independently, and a change to one integration rebuilds one crate rather than invalidating the monolith.
- In a single crate, every integration's code shares one compilation unit, so touching the core or any enabled integration recompiles all enabled integrations; this is the mechanism behind Vector's 4x figure and AWS's parallelism argument.
- With `--all-features` (used by docs.rs when configured that way, and by many CI setups), a single crate with hundreds of integrations must compile all vendor dependencies in one 15-minute, 6.4 GB docs.rs build. Crate-per-integration gives each integration its own docs.rs budget.
- Lockfile size scales with optional dependencies regardless of which features a consumer enables, because Cargo resolves optional dependencies into `Cargo.lock`; a monolith with hundreds of vendor-specific dependencies passes that cost to every user. I did not find a primary source quantifying this, so treat it as known Cargo behaviour rather than a sourced measurement.

### Gaps
- No primary-source measurement of dependency-resolution time or `Cargo.lock` size as a function of optional-dependency count was found.
- No published binary-size comparison between feature-gated monolith and crate-per-backend designs was found; with dead-code elimination the two should be similar, but that is unsourced.
- The AWS issue's maintainer analysis (root causes, mitigations) was not captured by my fetch; only the opening numbers are sourced.
- CI cost figures (minutes, runner spend) for OpenDAL, Vector or AWS were not found.

## 4. Feature-flag pitfalls

### Takeaway
Cargo features are unified across the whole dependency graph and must be additive; removing a feature or an implicitly-exposed optional dependency is a breaking change, so integration names become permanent API. `dep:` and `?` syntax (stable since Rust 1.60) are the tools that keep optional dependencies out of the public feature namespace.

### Cited Findings
- Unification: "When a dependency is used by multiple packages, Cargo will use the union of all features enabled on that dependency when building it." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- Additivity: "features should be _additive_. That is, enabling a feature should not disable functionality, and it should usually be safe to enable any combination of features. A feature should not introduce a SemVer-incompatible change." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- Mutually exclusive features "should be avoided if at all possible, because it requires coordinating all uses of the package in the dependency graph to cooperate to avoid enabling them together." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- Adding is minor: "It is usually safe to add new Cargo features." Removing is major: "It is usually a breaking change to remove Cargo features. This will cause an error for any project that enabled the feature." Mitigation: "Leave the old feature in `Cargo.toml`, but otherwise remove its functionality. Document that the feature is deprecated, and remove it in a future major SemVer release." — [Cargo Book, SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)
- Optional dependencies leak as features: "When there is an optional dependency, cargo implicitly defines a feature of the same name ... This problem can be avoided by using the `dep:` syntax in the `[features]` table, which disables this implicit feature. Using `dep:` makes it possible to hide the existence of optional dependencies under more semantically-relevant names which can be more safely modified." — [Cargo Book, SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)
- Recommended shape: "Use high-level features which enable optional dependencies, and document those as the preferred way to enable the extended functionality." — [Cargo Book, SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)
- `dep:` and weak dependency features (`"package-name?/feature-name"`, which "will only enable the given feature if something else enables the optional dependency") are "only available starting with Rust 1.60" — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- Real use of the weak syntax in a facade: `sqlx` `postgres = ["sqlx-postgres", "sqlx-macros?/postgres"]` — [sqlx 0.9.0](https://crates.io/api/v1/crates/sqlx/0.9.0)
- Public/private dependency marking is still unstable: "The 'public-dependency' feature allows marking dependencies as 'public' or 'private'" (tracking issue rust-lang/rust#44663) — [Cargo Book, Unstable features (nightly)](https://doc.rust-lang.org/nightly/cargo/reference/unstable.html)
- Dependencies in the public API as a semver hazard, in a maintainer's words (sqlx removing its `git2` feature): "We have to be careful with the crates we add to our public API as each one introduces yet another semver hazard." — [sqlx CHANGELOG](https://github.com/launchbadge/sqlx/blob/main/CHANGELOG.md)
- Documenting features: Cargo says "You are encouraged to document which features are available in your package. This can be done by adding doc comments at the top of `lib.rs`." — [Cargo Book, Features](https://doc.rust-lang.org/cargo/reference/features.html)
- `#[doc(cfg(...))]` / `#[doc(auto_cfg)]` are still listed in rustdoc's unstable features on the master branch (2026-10-08): "currently possible through the following unstable feature: `doc_cfg`" — [rustdoc unstable-features.md](https://github.com/rust-lang/rust/blob/master/src/doc/rustdoc/src/unstable-features.md)
- docs.rs sets a `docsrs` cfg: "To recognize Docs.rs from your Rust code, you can test for the `docsrs` cfg"; it "only applies to the final rustdoc invocation" and "does not apply to dependencies" — [docs.rs, About builds](https://docs.rs/about/builds)
- Rust 2024 edition Cargo changes: the default resolver now considers `rust-version`; "Changes how `default-features = false` works with inherited workspace dependencies" — [Rust Blog, Rust 1.85.0](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)

### Inferences
- In a one-crate design, if the Slack integration exposes a type from a vendor SDK crate and that SDK ships a major version, the whole library needs a major bump even though only one feature changed. In a crate-per-integration design only that crate bumps. This is the same hazard sqlx names, multiplied by the number of integrations.
- Because unification is graph-wide, any transitive dependency enabling `features = ["salesforce"]` forces that integration's dependencies into every build of the library in the graph; integrations must never change the behaviour of core or of each other.
- Feature labels on docs.rs still require the nightly-only `doc_cfg` gate behind `cfg(docsrs)`; this works on docs.rs because it builds with nightly, but local stable `cargo doc` will not show the labels.
- Feature names are effectively forever: renaming `gdrive` to `google-drive` requires keeping the old name as an alias until the next major release. OpenDAL keeping `services-*` after its RFC proposed `service-*` is an example of that pressure.

### Gaps
- The Cargo SemVer chapter text I retrieved does not contain an explicit rule on dependency major bumps leaking through re-exported types; the hazard is documented here only via the sqlx maintainer statement.
- I did not verify the `document-features` crate (auto-generating feature docs from `Cargo.toml` comments) or the status of Cargo's feature-metadata RFC from a primary source in this session; both should be checked before being cited.
- I did not verify which `[package.metadata.docs.rs]` keys (`features`, `all-features`, `rustdoc-args`) are documented today; the fetched page only showed `rustc-args`.

## 5. Semver and release cadence when third-party APIs change constantly

### Takeaway
Projects split into two camps: lockstep (every crate shares one version and release date: OpenDAL, opentelemetry, bevy, sqlx, rig) and independent (each backend crate has its own version: AWS, Google Cloud, Azure, embassy). Independent versioning is what the high-churn, high-count SDKs chose, and it requires release automation; lockstep is simpler but makes every backend's breaking change everyone's release.

### Cited Findings
- AWS RFC 0012 "Independent Crate Versioning": the earlier scheme kept consistent `major.minor` across all crates; under the proposal a generated service crate's version increments when the code-generator version changes or the service model changes, tracked by hashes in a `versions.toml` manifest; minor bumps cover "model updates with API changes", patch bumps cover "documentation-only model updates"; CI fails if a runtime crate's source changes without a version bump; yanking is done per dated release tag (`YYYY-MM-DD`) across all crates in that release — [smithy-rs RFC 0012](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/rfcs/rfc0012_independent_crate_versioning.md)
- AWS cadence evidence: `aws-sdk-ec2` at 1.267.0 with 331 published versions, `aws-sdk-s3` at 1.152.0 with 204, `aws-sdk-dynamodb` at 1.130.0 with 188, all last published 2026-10-01; `aws-config` is at 1.12.0 — [aws-sdk-ec2](https://crates.io/api/v1/crates/aws-sdk-ec2), [aws-sdk-s3](https://crates.io/api/v1/crates/aws-sdk-s3), [aws-sdk-dynamodb](https://crates.io/api/v1/crates/aws-sdk-dynamodb), [aws-config](https://crates.io/api/v1/crates/aws-config)
- Lockstep examples (registry snapshot 2026-10-08): `opentelemetry`, `opentelemetry_sdk`, `opentelemetry-otlp`, `opentelemetry-http` all 0.33.0 on 2026-09-18; `bevy` and `bevy_ecs` both 0.20.0-rc.2 on 2026-09-28; `sqlx`, `sqlx-core`, `sqlx-postgres` all 0.9.0 on 2026-05-21; `rig-core`, `rig-mongodb`, `rig-bedrock` all 0.44.0 on 2026-10-07; OpenDAL core/service/layer crates all 0.59.4 on 2026-10-05 — [opentelemetry](https://crates.io/api/v1/crates/opentelemetry), [opentelemetry-otlp](https://crates.io/api/v1/crates/opentelemetry-otlp), [bevy_ecs](https://crates.io/api/v1/crates/bevy_ecs), [sqlx-postgres](https://crates.io/api/v1/crates/sqlx-postgres), [rig-mongodb](https://crates.io/api/v1/crates/rig-mongodb), [opendal-service-s3](https://crates.io/api/v1/crates/opendal-service-s3)
- Independent examples: `embassy-executor` 0.10.0, `embassy-time` 0.5.1, `embassy-stm32` 0.6.0 (all 2026-03-20); `google-cloud-storage` 1.20.0 vs `google-cloud-secretmanager-v1` 1.14.0 vs `google-cloud-gax` 1.15.0; `azure_core` 1.2.0-beta.1 vs `azure_storage_blob` 1.1.0 — [embassy-executor](https://crates.io/api/v1/crates/embassy-executor), [embassy-time](https://crates.io/api/v1/crates/embassy-time), [google-cloud-gax](https://crates.io/api/v1/crates/google-cloud-gax), [azure_storage_blob](https://crates.io/api/v1/crates/azure_storage_blob)
- Lockstep still means frequent breaking releases for a pre-1.0 multi-backend library: OpenDAL's upgrade guide has separate breaking-change sections for v0.57, v0.58 and v0.59 (for example `Operator::new(builder)` now returns `Result<Operator>`; `Metadata` constructors replaced by `MetadataBuilder`), all within 2026 — [OpenDAL upgrade.md](https://github.com/apache/opendal/blob/main/core/core/src/docs/upgrade.md)
- OpenDAL's stated cost of splitting: "Increased release coordination complexity across multiple crates" — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)

### Inferences
- The umbrella-crate pattern buys import ergonomics and a single "known-good set" version, but it does not by itself buy independent cadence: every lockstep project above has an umbrella or core crate, and they still release everything together. Independent cadence comes from independent crate versions plus a stable 1.x core that integration crates depend on with a caret range (AWS, Google, Azure all have a 1.x core).
- For a SaaS-connector library the core crate's stability is the gating factor. While core is 0.x and breaking (OpenDAL: three breaking minors in about five months), every integration crate must re-release on each core break, which is lockstep in practice whatever the versioning policy says.
- A facade crate that pins exact integration versions must itself release whenever any integration releases; at hundreds of integrations with weekly vendor changes that is a near-daily facade release. AWS's choice of no facade avoids this.
- In a single-crate design there is only one version, so a breaking change to one vendor's API surface forces a semver-major (or 0.x minor) for all users, including those who never enabled that feature.

### Gaps
- I did not find maintainer statements from opentelemetry, bevy, embassy or tower-http explaining their versioning choice; the lockstep/independent classification is inferred from registry data only.
- AWS RFC 0012 is marked "Status: RFC" in the file I read; I did not verify how closely the GA SDK's release tooling follows it, beyond the observed independent versions.
- Whether OpenDAL intends to move to independent service versions after 1.0 is not stated in the sources I read.

## 6. Shared core design

### Takeaway
The successful multi-backend core (OpenDAL) is small: one backend trait with default methods that return a typed `Unsupported` error, a capability struct that tests and users query, an error type that carries a retry-relevant status, and middleware layers kept outside core unless they protect correctness. On stable Rust the public backend trait is written as `fn ... -> impl Future + Send`, with a separate object-safe wrapper for dynamic dispatch.

### Cited Findings
- Async traits in stable Rust: "Rust 1.75 ... will include support for both `-> impl Trait` notation and `async fn` in traits." The compiler warns "use of `async fn` in public traits is discouraged as auto trait bounds cannot be specified"; the suggested fix is to "desugar to a normal `fn` that returns `impl Future` and add any desired bounds such as `Send`", or use `trait-variant`. "Traits that use `-> impl Trait` and `async fn` are not object-safe"; for `dyn Trait` the post points to `#[async_trait]` — [Rust Blog, 2023-12-21](https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits/)
- OpenDAL's backend trait follows exactly that guidance (raw, `core/core/src/raw/accessor.rs`): methods are declared as `fn stat(...) -> impl Future<Output = Result<RpStat>> + MaybeSend;`, optional operations have default bodies returning `ErrorKind::Unsupported`, `read`/`write`/`list` return associated `Self::Reader` / `Self::Writer` / `Self::Lister` types, and a second object-safe form (`async fn stat(...)`, `oio::Reader`) exists for type-erased use — [OpenDAL accessor.rs](https://github.com/apache/opendal/blob/main/core/core/src/raw/accessor.rs)
- OpenDAL's error taxonomy (raw, `core/core/src/types/error.rs`): `ErrorKind` variants `Unexpected`, `Unsupported`, `ConfigInvalid`, `NotFound`, `PermissionDenied`, `IsADirectory`, `NotADirectory`, `AlreadyExists`, `RateLimited`, `IsSameFile`, `ConditionNotMatch`, `RangeNotSatisfied`, plus an orthogonal `ErrorStatus` (`Temporary` / `Persistent`) exposed as `is_temporary()` / `is_persistent()` / `is_permanent()` — [OpenDAL error.rs](https://github.com/apache/opendal/blob/main/core/core/src/types/error.rs)
- Which layers stay in core: `ErrorContext`, `Simulate`, `Complete`, `CorrectnessCheck`, `CapabilityCheck`, `ImmutableIndex`, `HttpClient`; everything else (retry, logging, metrics, tracing, timeout, throttle, ...) is a separate `opendal-layer-*` crate. Rationale: "Placing correctness-critical layers in core prevents invariant violations." The RFC leaves open whether `Retry` and `TailCut` count as critical — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)
- Facade defaults after the split: `default = ["auto-register-services", "http-transport-reqwest", "executors-tokio", "layers-concurrent-limit", "layers-logging", "layers-retry", "layers-timeout"]`; HTTP transport and executor are swappable features rather than hard dependencies of core — [opendal 0.59.4](https://crates.io/api/v1/crates/opendal/0.59.4)
- Runtime registration: each service crate exposes a `register(&OperatorRegistry)` helper and the facade "registers enabled services via `ctor` initialization" so that `Operator::from_uri` works without core knowing the services — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)
- What OpenDAL's maintainers are changing in hindsight (RFC 7700, start date 2026-06-05): the public API exposed both `native_capability()` and `full_capability()`; "The names describe implementation history rather than the contract callers should rely on", and developers "can misread the service capability and incorrectly conclude a feature is unavailable". The fix is one `OperatorInfo::capability()` meaning the effective capability after layers, with the service-declared capability kept internal. Stated cost: "significant refactoring across services and layers" plus deprecated aliases until the next breaking window — [OpenDAL RFC 7700](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/7700_capability_api.md)
- What sqlx's maintainers gave up when splitting: `Executor` impls for `Transaction` and `PoolConnection` "cannot exist in the new crate architecture without rewriting the `Executor` trait entirely" (a core trait designed for one crate did not survive the split unchanged) — [sqlx CHANGELOG](https://github.com/launchbadge/sqlx/blob/main/CHANGELOG.md)
- smithy-rs rule for where behaviour lives: "If the behavior is relevant to all services: Behavior like this should be defined as a middleware. ... If the behavior is only relevant to some services/depends on service model specifics", it belongs in the per-operation generated code; request signing is the example of the former — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)
- smithy-rs keeps `serde` out of generated service types for compile-time and correctness reasons ("We can't use `serde` for serializing requests to AWS ... both sides of that process would require too much customization") — [smithy-rs design FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md)

### Inferences
- OpenDAL's model works because every backend maps to one narrow verb set (read, write, stat, list, delete, ...). SaaS integrations do not share a verb set (Slack messages, Jira issues, Salesforce objects), so a connector library's shared core is likely limited to auth/credentials, HTTP transport, pagination, rate-limit and retry semantics, error taxonomy and capability/metadata description, with per-integration typed APIs on top. That makes the AWS/Google shape (thin shared runtime, per-service API crates) a closer fit than OpenDAL's single-trait shape for anything beyond the common plumbing.
- Design the core trait for crate boundaries from day one: the sqlx and OpenDAL experiences both show that traits and capability APIs designed inside a monolith needed breaking changes when backends moved to separate crates.
- Expose one "effective capability" query and keep backend-declared capability internal; split the error type into kind plus a retryable/temporary status so generic retry middleware does not need per-vendor knowledge.
- Keep the HTTP client, TLS backend and async runtime behind core features or traits rather than hard dependencies, as OpenDAL's `http-transport-*` and `executors-tokio` features do; otherwise feature unification forces one choice on every integration.

### Gaps
- I did not retrieve `tower`/`tower-http` design documents or `object_store`'s trait definition in this session, so comparisons with tower's `Service`/`Layer` model are not sourced here.
- No explicit "what we would do differently" retrospective from AWS SDK, Vector or Rig maintainers was found; the hindsight evidence is limited to OpenDAL RFCs 6828/7700 and the sqlx 0.7 changelog.
- Whether `dyn`-compatible async traits have become available in stable Rust between 1.75 and 1.99 was not checked; OpenDAL's continued use of a separate dyn wrapper suggests the two-trait pattern is still current, but that is inference.

## 7. Contribution and governance at scale

### Takeaway
OpenDAL's answer to backend rot is a single shared behavior-test suite that every service runs against a real or containerised endpoint in CI, with tests selected by the capabilities the service declares, plus a published definition of "stable"; it does not use per-service CODEOWNERS. Vector enforces structure by rule (every component behind its own feature) and a dedicated feature-check target.

### Cited Findings
- Purpose (raw): "Behavior tests are used to make sure every service works correctly." Configuration is by environment variable per backend; run with `OPENDAL_TEST=fs cargo test behavior --features tests` — [OpenDAL behavior tests README](https://github.com/apache/opendal/blob/main/core/tests/behavior/README.md)
- Capability-driven selection (raw): "Behavior tests are selected by the operator's full capability. Test setups can override capability with `OPENDAL_TEST_CAPABILITY_OVERRIDES`", for example `stat_with_version=false,read_with_version=false,delete_max_size=700` — [OpenDAL behavior tests README](https://github.com/apache/opendal/blob/main/core/tests/behavior/README.md)
- Silent-skip default (raw): "If the env variables are not set, all behavior tests will be skipped by default." — [OpenDAL behavior tests README](https://github.com/apache/opendal/blob/main/core/tests/behavior/README.md)
- Coverage is partial: `.github/services/` has setups for 47 services on 2026-10-08, against 68 `services-*` features on the facade — [.github/services listing](https://api.github.com/repos/apache/opendal/contents/.github/services), [opendal 0.59.4](https://crates.io/api/v1/crates/opendal/0.59.4)
- One service is tested against several real and compatible endpoints: `.github/services/s3/` contains 14 setups (`aws_s3`, `aws_s3_express`, `aws_s3_with_versioning`, `aws_s3_with_sse_c`, `ceph_rados_s3`, `r2`, `seaweedfs_s3`, ...) — [.github/services/s3 listing](https://api.github.com/repos/apache/opendal/contents/.github/services/s3)
- Live-service secrets in CI (raw, `aws_s3/action.yml`): the composite action uses `1Password/load-secrets-action` with references such as `OPENDAL_S3_ACCESS_KEY_ID: op://services/s3/access_key_id`, and its description records who pays: "Behavior test for AWS S3. This service is sponsored by @datafuse_labs." The same file sets capability overrides for that particular endpoint — [OpenDAL aws_s3 action.yml](https://github.com/apache/opendal/blob/main/.github/services/s3/aws_s3/action.yml)
- Stability definition (2024-01-22): "OpenDAL now supports 59 services, although only some of them are _stable_." A stable service must "Have integration tests covered" and "Have at least one production user" — [OpenDAL graduation blog](https://opendal.apache.org/blog/apache-opendal-graduated)
- Community size at graduation: 19 committers, 164 contributors, 2,400+ pull requests; "Used by 10 known entities" — [OpenDAL graduation blog](https://opendal.apache.org/blog/apache-opendal-graduated)
- CODEOWNERS is per language binding, not per service (raw): `* @Xuanwo @tisonkun`, `/core @Xuanwo`, `/bindings/java/ @tisonkun`, `/bindings/python/ @messense @Zheaoli`, ... — [OpenDAL CODEOWNERS](https://github.com/apache/opendal/blob/main/.github/CODEOWNERS)
- After the split, "Each service crate includes unit tests and behavior validation through shared harness"; whether the harness becomes a shared test crate or distributed fixtures is listed as unresolved — [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md)
- Vector: integration tests need "`docker` available, or a real live version of that service"; `make check-component-features` checks each component's feature in isolation; dependency additions are reviewed under a written guide — [vector DEVELOPING.md](https://github.com/vectordotdev/vector/blob/master/docs/DEVELOPING.md)
- AWS avoids the problem by generation: a crate changes only when the generator or the service model changes, tracked by hashes in `versions.toml` — [smithy-rs RFC 0012](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/rfcs/rfc0012_independent_crate_versioning.md)
- Hand-maintained wide coverage tends to stall: `google-apis-rs` is in "Maintenance Mode" with updates "probably no more than twice a year" — [google-apis-rs README](https://github.com/Byron/google-apis-rs/blob/main/README.md)

### Inferences
- About 21 of OpenDAL's 68 services have no CI behavior-test setup, and the test default is to skip when credentials are absent. A new library should make "has live conformance tests in CI" the visible tier boundary and fail loudly, not skip, when a tier-1 integration's credentials are missing.
- Live testing of SaaS integrations is harder than storage: there is no MinIO-style local emulator for most vendors, sandboxes are per-account, and tokens expire. OpenDAL's model of a named sponsor per live endpoint ("sponsored by @datafuse_labs") is the only sustainable pattern I saw for paying for and owning those credentials.
- Capability-selected conformance tests transfer well: each integration declares what it supports, and the shared suite runs only the matching tests, so adding an integration does not require writing its core test matrix.
- Crate-per-integration makes tiering mechanical (per-crate README badge, per-crate version, per-crate ownership, ability to yank or deprecate one integration) in a way feature flags in one crate cannot.

### Gaps
- OpenDAL's current count of stable services and any formal tier list were not found; the "stable" definition is from the 2024 graduation post and may have evolved.
- I did not find documented per-backend ownership rules (CODEOWNERS per integration) in any of the projects examined; whether Vector uses them was not checked.
- No source was found describing how OpenDAL or Vector removes abandoned backends (deprecation policy, timelines).

## 8. Licensing and legal considerations

### Takeaway
Vendor API terms attach to whoever holds the API credentials and commonly forbid redistributing or sublicensing API access and embedding credentials in open-source code, so the library must be bring-your-own-credentials; vendor names in feature and crate names rest on descriptive (nominative) use and should avoid implying endorsement. crates.io prohibits name squatting and defers legal disputes to the Rust Foundation.

### Cited Findings
- Google APIs Terms of Service (last modified 2021-11-09), section 4.a: you will not "Sublicense an API for use by a third party" and "will not create an API Client that functions substantially the same as the APIs and offer it for use by third parties"; reverse engineering is prohibited; section 4.b: "Developer credentials may not be embedded in open source projects." Section 6: Google Brand Features may only be used "in accordance with the Terms" — [Google APIs Terms of Service](https://developers.google.com/terms)
- Slack API Terms of Service (effective 2025-10-10): you may not "access our APIs in order to replicate or compete with the Services"; "you may not sell, rent, lease, sublicense, redistribute or syndicate access to any of our APIs"; may not exceed rate limits; may not "use API Data to train a large language model" or "bulk export Slack message and file data except where expressly allowed"; apps distributed commercially beyond your own organisation need marketplace approval or a partner agreement — [Slack API Terms of Service](https://slack.com/terms-of-service/api)
- Slack brand terms: use of the name and marks is permitted "only in limited circumstances"; "Slack" should be used as an adjective followed by a descriptor, not as a noun, verb, plural or possessive (from a search summary of the page, not a direct fetch) — [Slack Brand Terms of Service](https://brand.slackhq.com/terms-of-service)
- Notion's Developer Terms govern API use for building integrations and prohibit disassembling, decompiling or reverse engineering the API (search summary, not a direct fetch) — [Notion Developer Terms](https://notion.notion.site/Developer-Terms-ba4131408d0844e08330da2cbb225c20)
- crates.io policy (RFC 3463, dated 2023-07-24): prohibits a crate that "exists only to reserve a name for a prolonged period of time (often called 'name squatting') without having any genuine functionality, purpose, or significant development activity", and trading names for compensation; on legal matters "the crates.io team will respect the legal decisions of the Rust Foundation"; enforcement includes "account suspension, account termination, or removal of content"; contact help@crates.io — [RFC 3463](https://rust-lang.github.io/rfcs/3463-crates-io-policy-update.html)
- Existing practice of vendor names in crate names without apparent challenge: `aws-sdk-s3`, `azure_storage_blob`, `google-cloud-storage` (first-party), and third-party `opendal-service-github`, `rig-mongodb`, `rig-bedrock` — [opendal-service-github](https://crates.io/api/v1/crates/opendal-service-github), [rig-mongodb](https://crates.io/api/v1/crates/rig-mongodb), [rig-bedrock](https://crates.io/api/v1/crates/rig-bedrock)
- OpenDAL is licensed Apache-2.0 under the ASF (license header in repository files) — [OpenDAL aws_s3 action.yml](https://github.com/apache/opendal/blob/main/.github/services/s3/aws_s3/action.yml)

### Inferences
- The terms quoted bind the party that accepts them when obtaining API credentials. A library that ships no credentials, and whose users register their own apps with each vendor, is a tool rather than a redistribution of API access; a hosted service that proxies many customers through one credential is what the "sublicense / redistribute / syndicate" clauses target. This is my reading, not legal advice, and the Google "functions substantially the same as the APIs" clause is broad enough to merit counsel review for a generic connector product.
- Never embed OAuth client IDs/secrets for vendor apps in the repository or published crates (Google's terms say so explicitly); test credentials belong in a secrets manager, as in OpenDAL's 1Password setup.
- Reserving hundreds of `mylib-<vendor>` crate names ahead of real implementations would fall under crates.io's squatting prohibition; publish an integration crate only when it has genuine functionality.
- Publishing one crate per vendor puts the vendor's mark in a package name; the pattern `<project>-<vendor>` or `<project>-service-<vendor>` (project name first) is what existing third-party projects use and reads as descriptive rather than as an official client. Vendor logos should stay out of the repository.
- Per-vendor data-use restrictions (Slack's ban on LLM training and bulk export) apply to the library's users; documenting them per integration is a governance task that scales with integration count.

### Gaps
- I did not verify from a primary source in this session the Rust ecosystem's dual MIT/Apache-2.0 convention (the Rust API Guidelines' permissive-license item is the place to confirm) or the license of each compared project other than OpenDAL.
- Terms for Salesforce, Atlassian/Jira, Linear, GitHub and Notion were not read directly; only Google and Slack were fetched. LinkedIn/X-style restrictive API terms were not examined.
- No case was found of a vendor forcing a rename or takedown of a Rust crate on trademark grounds; absence of evidence only.
- Whether RFC 3463 was merged as written and matches the live policy page at crates.io/policies was not confirmed (the fetched page showed it as an RFC).

## 9. Comparison of the viable packaging options

### Takeaway
For "hundreds to thousands" of integrations the single crate with one feature per integration is ruled out by the 300-feature cap and by lockstep semver; the evidence favours one crate per integration on a small stable core, with an optional facade that covers only a curated subset or is split by category, and declarative/runtime-loaded definitions as the route past roughly the hundreds.

### Cited Findings

### Inferences
- Start as B, structured so it can degrade gracefully into C: publish `core` + `<project>-<vendor>` crates from the first release, and treat the facade as a convenience over a curated set. This keeps the `features = ["slack", "github"]` experience, and the 300-feature facade cap then limits only what the facade advertises, not what exists.
- Beyond about 250 integrations the facade must either stop growing (new integrations are separate crates only), split into category facades (each under 300 features and 500 dependencies), or be dropped as AWS did. Plan the naming for that now, because feature and crate names cannot be changed without a breaking release.
- Option A is defensible only for a first handful of integrations in a prototype, and migrating off it later is a breaking, months-long project (OpenDAL: RFC 2025-11-27, shipped 2026-05-01, about 70 extraction tasks) with trait redesign risk (sqlx).
- Independent per-integration versions (the main benefit of C) are only real once the core is 1.x-stable; until then B and C behave the same and lockstep releases are simpler.
- For the long tail (the difference between hundreds and thousands), compiled Rust code per integration multiplies CI, review and credential-sponsorship costs linearly. A declarative definition format interpreted by the core, or code generated from vendor OpenAPI specs in the way AWS generates from Smithy models, is the only approach in this evidence that scaled past about 450 units with a small team, and both of those are generated, not hand-written.

### Gaps
- Option D has no directly comparable Rust precedent in the sources I read (no Rust library that loads SaaS connector definitions at runtime was examined); the non-Rust declarative connector ecosystems were out of this note's scope and should come from the adjacent research threads.
- No project publishes a cost comparison between B and C (release tooling effort, CI minutes); the trade-off above is reasoned from structure, not measured.
- Cargo features that could change this calculus are still unstable as of the nightly docs read on 2026-10-08 (`public-dependency`, `feature-unification`, `open-namespaces`); I could not confirm the status of multi-package workspace publishing or feature metadata because the Cargo changelog fetch failed and the unstable-features page was only partially read (first 100,000 of about 109,000 characters) — [Cargo Book, Unstable features (nightly)](https://doc.rust-lang.org/nightly/cargo/reference/unstable.html)
