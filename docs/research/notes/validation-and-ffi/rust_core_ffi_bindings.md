## 1. Precedents: which production libraries ship a Rust core with bindings in several languages, and how?

### Takeaway
The pattern is established and in production for network-heavy async libraries (Temporal, Valkey GLIDE, 1Password SDK, Bitwarden, LiveKit, Statsig, OpenDAL, iroh, Matrix), but no project uses one binding tool for all languages: each uses a per-language tool (napi-rs or neon, PyO3, JNI, UniFFI for Kotlin/Swift, a C ABI for Go/.NET/others). The projects that reach five or more languages with a small team do it by pushing one narrow message-shaped entry point through a C ABI or WASM, not by exposing a typed Rust API per language.

### Cited Findings

**Apache OpenDAL (closest structural analogue: many backends, async I/O)**
- The `bindings/` directory holds 17 language directories on 2026-10-08: c, cpp, d, dart, dotnet, go, haskell, java, lua, moonbit, nodejs, ocaml, php, python, ruby, swift, zig — [apache/opendal bindings/](https://github.com/apache/opendal/tree/main/bindings)
- Only three are listed as released (raw): "Released Bindings: Java, Node.js, Python"; "Unreleased Bindings: C, C++, C#, D, Dart, .NET, Go, Haskell, Lua, OCaml, PHP, Ruby, Swift, Zig" — [bindings/README.md](https://github.com/apache/opendal/blob/main/bindings/README.md); contradicted for Go by the Go binding's own README, which carries a "status-released" badge and a pkg.go.dev link — [bindings/go/README.md](https://github.com/apache/opendal/blob/main/bindings/go/README.md)
- Bindings are versioned independently of the core (raw): "We release each binding independently of the `opendal` crate (Rust core). ... while the `opendal` crate might be at version `0.55.0`, a binding might be at version `0.47.0` or `0.49.2`." — [bindings/README.md](https://github.com/apache/opendal/blob/main/bindings/README.md). Registry snapshot: npm `opendal` 0.49.12 (2026-10-05), PyPI `opendal` 0.47.10 (2026-09-22), Maven `org.apache.opendal:opendal` 0.50.7 (2026-10-01), against core crate 0.59.4 — [npm opendal](https://registry.npmjs.org/opendal/latest), [PyPI opendal](https://pypi.org/pypi/opendal/json), [Maven opendal](https://repo1.maven.org/maven2/org/apache/opendal/opendal/0.50.7/)
- Each binding is hand-written with a different tool, not generated from one definition (raw `Cargo.toml` files): Node.js uses `napi = "3.2.2"` + `napi-derive` + `tokio`; Python uses `pyo3 >= 0.29.1` + `pyo3-async-runtimes >= 0.29.0` with `tokio-runtime`; Java uses `jni = "0.22.4"`; Ruby uses `magnus = "0.8"` + `rb-sys`; C uses `cbindgen = "0.29.0"` over the core's `blocking` feature plus a Tokio runtime; .NET is a `cdylib` with `publish = false` — [nodejs/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/nodejs/Cargo.toml), [python/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/python/Cargo.toml), [java/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/java/Cargo.toml), [ruby/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/ruby/Cargo.toml), [c/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/c/Cargo.toml), [dotnet/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/dotnet/Cargo.toml)
- Go does not use cgo (raw): "opendal-go is a **Native** Go binding for Apache OpenDAL. It is built on top of `opendal-c` without CGO enabled, using purego and libffi." and "opendal-go requires **libffi** to be installed." — [bindings/go/README.md](https://github.com/apache/opendal/blob/main/bindings/go/README.md)
- Async crossing in OpenDAL: Python converts Rust futures to awaitables with `future_into_py` (GitHub code search: 3 files, `bindings/python/src/operator.rs`, `file.rs`, `lister.rs`); Java owns a Tokio runtime inside the native library (`struct Runtime { inner: Option<tokio::runtime::Runtime> }`, registered in `JNI_OnLoad`, with the comment "Operators, derived resources, and in-flight tasks own the runtime. The cache must not keep JVM-attached workers alive after those owners are released.") — [bindings/python/src](https://github.com/apache/opendal/tree/main/bindings/python/src), [bindings/java/src/executor.rs](https://github.com/apache/opendal/blob/main/bindings/java/src/executor.rs)
- Ownership is per binding, not per service: CODEOWNERS assigns `/bindings/java/` and `/bindings/python/` to named individuals (already recorded in the packaging note) — [OpenDAL CODEOWNERS](https://github.com/apache/opendal/blob/main/.github/CODEOWNERS)

**Temporal sdk-core (async network client plus state machines; the best-documented precedent)**
- The core repository (GitHub API now returns it as `temporalio/sdk-rust`, 530 stars) states it is "currently used as the base of: TypeScript SDK, Python SDK, .NET SDK, Ruby SDK" — [sdk-core README](https://github.com/temporalio/sdk-core/blob/master/README.md)
- Bridge per language (raw): "we use neon to support the TS/JS SDK, and we use PyO3 for Python. Languages using libraries like that layer another crate on top of `core` ... Other SDKs (ex: .NET) directly use C bindings available in this repo at core-c-bridge." — [sdk-core ARCHITECTURE.md](https://github.com/temporalio/sdk-core/blob/master/ARCHITECTURE.md)
- The boundary is message-shaped, not a typed object API (raw): "We define the interface between the core and lang SDKs (mostly) in terms of gRPC service definitions. The actual implementations of this 'service' are not generated by gRPC generators, but the messages themselves are, and make it easier to hit the ground running in new languages." The language side polls: "The lang sdk will continuously call/poll the core SDK to receive new tasks" — [sdk-core ARCHITECTURE.md](https://github.com/temporalio/sdk-core/blob/master/ARCHITECTURE.md)
- Why a shared core at all: the client logic "isn't just a thin wrapper over HTTP/gRPC calls; the SDK needs to handle the reconciliation of events and their related state changes" (search summary of the 2021 post by Spencer Judge) — [Temporal blog, 2021-04-20](https://temporal.io/blog/why-rust-powers-core-sdk)
- Maintainer statements from the QCon SF 2025 talk (via summarising fetch of the transcript, treat as paraphrase): Java and Go SDKs predate the core and are not built on it; bridges "are also written in Rust ... defined as Rust crates that live in the language-specific repo"; "The thinner that you keep this stuff, the easier it is to not screw up"; the shared core "cut the new development time for new languages in half"; team grew from "five guys, four guys" to "10 guys on my team. We support currently seven languages" — [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)
- Packaging as shipped: `@temporalio/core-bridge` 1.24.0 is one npm package of 152,183,785 bytes unpacked containing five prebuilt `index.node` files of 26.1 to 30.8 MB each (`releases/x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`); `temporalio` 1.34.0 on PyPI has 7 `cp310-abi3` wheels of 13.8 to 15.4 MB — [npm core-bridge](https://registry.npmjs.org/@temporalio%2Fcore-bridge/latest), [unpkg file listing](https://unpkg.com/@temporalio/core-bridge@1.24.0/?meta), [PyPI temporalio](https://pypi.org/pypi/temporalio/json)

**Bitwarden (two SDKs, two strategies)**

### Inferences
- Two families exist. Typed-per-language projects (OpenDAL, LanceDB, Polars, Matrix, Mozilla) cover two to four languages well and leave the rest "unreleased" or in other repositories. Message-shaped projects (Temporal, 1Password, Bitwarden Secrets Manager, LiveKit, Delta Chat, Valkey GLIDE) cover five to eight languages. The difference tracks surface width, not team size.
- OpenDAL is the warning case for "bindings if needed tomorrow": with 5,408 stars and an ASF community, 14 of 17 binding directories are still not listed as released. The three released bindings carry their own version lines (0.47 to 0.50 against core 0.59); because numbering is independent by policy, those numbers do not show how far each binding's feature set lags the core, and I did not measure that.
- The two precedents closest to Socket's host-implemented `TokenStore` are Bitwarden's `ClientManagedTokens` (an async trait implemented in Kotlin/Swift/JS and called from Rust middleware) and Matrix's `ClientSessionDelegate` (synchronous save/retrieve of session tokens). Both exist only on the UniFFI and WASM paths, not on a JSON/C-ABI path.
- No precedent I examined exposes "hundreds of typed per-vendor operation clients" across languages. The widest typed surfaces (Matrix, LanceDB) are a single domain.

### Gaps
- Team size or maintenance-cost figures were found only for Temporal (about 10 engineers, seven languages, via transcript paraphrase) and Statsig (7 developers, 24 SDKs). Nothing comparable was found for OpenDAL, Bitwarden, BAML, LanceDB, 1Password or Valkey GLIDE.

The BAML CFFI README only says Go tests "will by default download and use a cached version of the library from GitHub releases" — [language_client_cffi README](https://github.com/BoundaryML/baml/blob/canary/engine/language_client_cffi/README.md)
- I did not inspect the contents of `@1password/sdk-core`; that it is a WASM build is likely from the name, size and file count but unverified.
- Which Cargo feature set the published OpenDAL wheels and npm packages are built with (`default` with 14 services or `services-all`) was not confirmed from the release workflows.
- Zenoh has per-language repositories (`zenoh-c`, `zenoh-python`, `zenoh-java`, `zenoh-kotlin`, `zenoh-go`, `zenoh-csharp`, `zenoh-ts`) but I verified only that the repositories exist, not how they bind.
- pydantic-core and automerge are synchronous and do no network I/O, so they say nothing about async crossing.

## 2. Counter-precedents: who moved away from a Rust core with bindings, and why?

### Takeaway
The clearest reversals are Prisma (Rust query engine replaced by TypeScript plus a WASM compiler, citing contribution barriers, per-platform binaries, incompatible runtimes and serialization overhead) and Infisical (a cross-language Rust SDK replaced by native per-language SDKs that call the REST API directly). Infisical is the nearest analogue to Socket in shape: a library whose job is authenticated HTTP calls.

### Cited Findings
- Prisma's stated reasons: "Contributing to the query engine requires a combination of Rust and TypeScript proficiency, reducing the opportunity for community involvement."; "Each operating system and OpenSSL library version needs its own binary, complicating deployments and slowing down development."; "Modern JavaScript runtimes, serverless, and edge environments aren't always compatible with large Rust binaries."; data "must be serialized from JavaScript to Rust and then back to JavaScript, reducing efficiency." Reported results: bundle from about "14 MB (7 MB gzipped)" to "1.6 MB (600 KB gzipped)"; `findMany` over 25,000 records "185 ms to 55 ms" (via summarising fetch; the page gave 2025-01-30 and was evidently updated later, since it mentions "v6.16+") — [Prisma blog, From Rust to TypeScript](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)
- Prisma went through all three architectures. Docs for v6: "Prisma Client loads the query engine as a Node-API library by default. You can alternatively configure Prisma to use the query engine compiled as an executable binary, which is run as a sidecar process alongside your application." and "The Node-API library approach is recommended since it reduces the communication overhead between Prisma Client and the query engine." In v7 "Queries are compiled to SQL using a TypeScript-based query compiler" — [Prisma docs, engines (v6)](https://www.prisma.io/docs/orm/v6/more/internals/engines)
- Infisical: the cross-language repository `Infisical/sdk` returns 404 from the GitHub API on 2026-10-08; the organisation now has per-language repositories (`go-sdk`, `python-sdk-official`, `node-sdk-v2`, `java-sdk`, `ruby-sdk`, `php-sdk`, `infisical-dotnet-sdk`, `infisical-cpp-sdk`, `rust-sdk`) — [Infisical GitHub organisation](https://github.com/Infisical)
- Infisical's Ruby README (raw): "This is the official native Ruby SDK — it talks directly to the Infisical REST API and has no Rust/FFI dependency. It replaces the deprecated `infisical-sdk` gem that was built on Infisical's legacy cross-language architecture, so it is **not** a drop-in replacement" — [Infisical/ruby-sdk README](https://github.com/Infisical/ruby-sdk/blob/main/README.md)
- Registry evidence of the switch: `infisical-python` 2.3.6 (Rust-based, 19 platform wheels of 6.3 to 7.0 MB, last upload 2025-04-17) had 29,628 downloads in the last month; its replacement `infisicalsdk` 1.0.17 (one pure-Python wheel of 21,981 bytes, uploaded 2026-08-17) had 1,532,033. `@infisical/sdk` 5.0.2 on npm is 413,290 bytes unpacked in 9 files — [PyPI infisical-python](https://pypi.org/pypi/infisical-python/json), [PyPI infisicalsdk](https://pypi.org/pypi/infisicalsdk/json), [pypistats infisicalsdk](https://pypistats.org/api/packages/infisicalsdk/recent), [npm @infisical/sdk](https://registry.npmjs.org/@infisical%2Fsdk/latest)
- Infisical's original rationale for the Rust design was the same one Socket is considering: "the overhead that comes with maintaining a large collection of SDKs" and a single-language SDK to cut "duplicate code across different SDKs" (search summary of Infisical's contributor docs) — [Infisical docs, SDK development](https://infisical.com/docs/contributing/sdk/developing)
- Delta Chat is retiring its in-process C binding, though not its Rust core (raw): "libdeltachat is going to be deprecated and only exists because Android, iOS and Ubuntu Touch are still using it. If you build a new project, then please use the jsonrpc api instead." — [chatmail/core README](https://github.com/chatmail/core/blob/main/README.md)
- Temporal did not move its two oldest SDKs onto the core, and the maintainer names user resistance: "People really don't like to run native extensions in these languages a lot of the time. Like Java with the JNI, and to an even greater extent, Go with cgo cause a bunch of operational concerns for people." (transcript paraphrase) — [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)
- A binding generator abandoned mid-flight: `livekit/uniffi-bindgen-node` states it "is no longer being actively developed. It is still in use ... But it is incomplete." Development moved to `uniffi-bindgen-react-native` — [livekit/uniffi-bindgen-node README](https://github.com/livekit/uniffi-bindgen-node/blob/main/README.md)
- Valkey GLIDE's Node binding dropped its socket-IPC layer for direct N-API calls (code comments quoted in section 1); this is a change of mechanism inside the Rust-core strategy, not a retreat from it — [node/rust-client/src/lib.rs](https://github.com/valkey-io/valkey-glide/blob/main/node/rust-client/src/lib.rs)

### Inferences
- The reversals share a profile: the logic in the core was simple enough to rewrite per language (REST calls plus auth for Infisical; query planning that could be compiled to WASM for Prisma), so the binary-distribution cost outweighed the duplication saved. The projects that stayed (Temporal, Statsig, 1Password, Matrix, Valkey GLIDE) have cores with logic that is hard to duplicate correctly: state machines, rule evaluation, cryptography, cluster topology.
- For Socket the question this raises is how much non-trivial shared logic the core holds. OAuth flows, token refresh with locking, retry, rate limiting and pagination are moderately complex; "POST a Slack message" is not. If operations dominate and they are thin, the Infisical outcome is the base rate.
- Prisma's four reasons map directly onto Socket: contributors must know Rust to add an integration; every platform needs a binary; edge runtimes cannot load native addons; every call serializes across the boundary.

### Gaps
- I found no first-party Infisical post explaining why it abandoned the Rust core; the reasons above are inferred from the README wording and package evidence.
- I did not research older shared-core post-mortems in C++ (for example Dropbox's mobile shared-code write-up) or any Rust-specific ones beyond those listed.
- I did not confirm the exact publication date and author of the Prisma post; the fetch tool reported 2025-01-30 and "Jon Harrell", which I could not cross-check.

## 3. Tooling state as of 2026: what is mature for async network libraries?

### Takeaway
Mature and demonstrated in production for async network libraries: napi-rs (Node), PyO3 with `pyo3-async-runtimes` (Python), UniFFI (Kotlin, Swift, Python), hand-written JNI (Java), and a C ABI with completion callbacks (Go, .NET, PHP, Ruby, C++). Not mature: UniFFI's third-party Go, C#, Java and Node generators (they trail UniFFI core and one Node generator is abandoned), PyO3's native `async fn`, and the WebAssembly Component Model outside Wasmtime and jco.

**WebAssembly Component Model**
- "WASI 0.3 is official" and "The 0.3.0 specification is now stable" (2026-06-11): "async is now native to WebAssembly Components", with "stream<T>, future<T>, and async as first-class constructs to the canonical ABI"; HTTP worlds become `wasi:http/service` and `wasi:http/middleware`. Hosts: "Wasmtime 45 runs the latest release candidate today, and Wasmtime 46 will ship WASI 0.3.0"; "jco, the JavaScript Component Model toolchain, also supports all of WASI 0.3". Guests: Rust `wit-bindgen` supports async; `componentize-go` supports it; for Python, JavaScript, C# and C "Async support for guest binding generators is also in-progress" (via summarising fetch) — [Bytecode Alliance, WASI 0.3](https://bytecodealliance.org/articles/WASI-0.3)
- Component Model 1.0 is not reached: it needs native implementation in at least two browser engines (Mozilla and Chrome are evaluating); cooperative threads will ship in "a follow-up WASI P3 minor release"; runtimes named as running components are Wasmtime, jco (by transpiling) and Gravity (built on wazero) (2026-06-08, via summarising fetch) — [Bytecode Alliance, The Road to Component Model 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)

- jco can "'Transpile' WebAssembly components into ES modules that can run in environments like NodeJS and the browser" and ships a `preview3-shim` "for NodeJS" — [jco README](https://github.com/bytecodealliance/jco/blob/main/README.md)
- Other runtimes (search summaries, not verified at source): wazero has no built-in Component Model and third-party layers exist (`wacogo`); Chicory (pure-Java) supports WASI preview 1; Extism has not adopted the Component Model because support is concentrated in Wasmtime — [wacogo on pkg.go.dev](https://pkg.go.dev/github.com/partite-ai/wacogo), [Extism issue #666](https://github.com/extism/extism/issues/666)

### Inferences
- Mature combinations for an async HTTP library today, each demonstrated by at least two production projects: Node via napi-rs with a library-owned Tokio runtime; Python via PyO3 + `pyo3-async-runtimes` (or UniFFI Python, as 1Password does); Kotlin/Swift via UniFFI with `async_runtime = "tokio"`; Java via hand-written JNI and `CompletableFuture`-style executors; Go and .NET via a C ABI with completion callbacks, or via WASM for Go.
- UniFFI is not a one-tool answer for Socket's stated languages. Its first-party targets are mobile-oriented; Node, Go, Java and C# all depend on third-party generators pinned to UniFFI 0.31 while core is at 0.32, and UniFFI's own changelog shows breaking changes "for external bindings authors" in consecutive releases.
- The Component Model became technically capable of this job only in June 2026 (async, streams, `wasi:http`), and the host side is still Wasmtime plus jco. Embedding components from Go, .NET or Java in process is not something any named production project demonstrably does.
- Java has two viable roads with opposite constraints: JNI works on every JDK but is being progressively gated (JEP 472), while FFM needs JDK 22+.

### Gaps
- I did not verify whether `uniffi-bindgen-go` and `uniffi-bindgen-cs` support async functions and async foreign traits; their READMEs' feature and limitation sections were not captured.
- I did not confirm which UniFFI version carries 0.32.2 changes: crates.io shows 0.32.2 (2026-09-23) while the changelog on `main` lists 0.32.1 (2026-09-08) as the latest tagged section.
- Diplomat's async support is unknown; the only signal is two closed 2026 issues about async with the Python (nanobind) backend. Its README still shows `diplomat = "0.10.0"` against 0.16.1 on crates.io.
- `boltffi` (crates.io 0.31.0, first published 2026-02-17, 29 versions) appeared in the registry query; I know nothing about it beyond those numbers.

## 4. Specific hard problems for this library and how precedents solve them

### Takeaway
Every hard problem has a working precedent, but the solutions constrain the core's API: host-implemented traits must be object-safe, owned-argument, `Send + Sync` and fallible; the library must own (or explicitly accept) a Tokio runtime; cancellation and streaming must be explicit handle- or cursor-based because none of the generic tools carries them across the boundary.

### Cited Findings

**Rust futures to host promises/coroutines**
- UniFFI: the foreign side polls. "For each async function, UniFFI generates 4 scaffolding functions" (`rust_future_poll`, `rust_future_complete`, `rust_future_free` and the constructor); the generated code calls poll with a callback until `RUST_FUTURE_READY` (raw) — [UniFFI async-overview.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/internals/async-overview.md)
- Node: `#[napi] async fn` futures run on the runtime napi manages and resolve a Promise (source cited in section 3); OpenDAL, LanceDB and Valkey GLIDE ship this.
- Python: `future_into_py` from `pyo3-async-runtimes` with the Tokio feature (OpenDAL `operator.rs`, `file.rs`, `lister.rs`); UniFFI Python has a documented corner case needing `uniffi_set_default_event_loop()` "when Python async functions run outside of the eventloop" — [futures.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/futures.md)
- C ABI: spawn on a library-owned runtime and invoke a completion callback (Bitwarden `run_command_async`, BAML `call_function_from_c`, Valkey `AsyncClient { success_callback, failure_callback }`), cited in section 1.
- Go: block the calling goroutine. Valkey GLIDE: "Each command blocks within its goroutine, but all 10 run concurrently"; 1Password's interface is `Invoke(ctx context.Context, invokeConfig []byte) ([]byte, error)` — [Valkey blog](https://valkey.io/blog/2025-03-4-go-client-in-public-preview/), [onepassword-sdk-go core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/core.go)
- Thread affinity is the trap for interpreter languages (Temporal transcript paraphrase): "All invocations that are going to go back and touch Ruby code need to happen on a thread that Ruby itself created" and a Tokio task "could run on some arbitrary thread that the Tokio executor spawned ... I can't invoke this Ruby callback here because Ruby doesn't own that thread." — [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)

**Who owns the Tokio runtime**
- UniFFI's default is no Rust runtime: "UniFFI can't rely on a Rust async runtime. We don't want to force library authors into a particular runtime." It works only if Rust awaits "UniFFI async callback/trait methods. This often means defining traits for things like HTTP clients so that Rust can leverage async HTTP libraries from the foreign side" or runtime-agnostic primitives (raw) — [async-overview.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/internals/async-overview.md)
- For Tokio-dependent code UniFFI offers `#[uniffi::export(async_runtime = "tokio")]`, "wrapping each method's FFI scaffolding future in `async_compat::Compat`" (0.32.0 extended it to trait exports); Bitwarden and Matrix use it — [uniffi-rs CHANGELOG](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md), [bitwarden-uniffi/src/lib.rs](https://github.com/bitwarden/sdk-internal/blob/main/crates/bitwarden-uniffi/src/lib.rs)
- Library-owned runtimes in practice: one per client object (Bitwarden `CClient { runtime, client }`); one process-global (`static RUNTIME` in BAML); a weakly cached default owned by live operators (OpenDAL Java); napi's built-in runtime with an opt-in replacement — sources in sections 1 and 3.
- Host-owned I/O instead of a Rust runtime: Mozilla's viaduct `Backend` (cited in section 1).

**A host-language object implementing a Rust trait (token store, HTTP callback)**
- UniFFI: documented with a `Keychain` example taking `Arc<dyn Keychain>`; requirements are `Send + Sync`, by-value parameters and `Result` returns (section 3). Demonstrated: Bitwarden `ClientManagedTokens` (async), Matrix `ClientSessionDelegate` (sync), Mozilla viaduct backend in Kotlin.
- WASM: host functions imported by name (1Password imports `random_fill_imported`, `unix_time_milliseconds_imported`, `utc_offset_seconds` through Extism) — [internal/imported.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/imported.go)
- C ABI / JSON designs: Bitwarden's Secrets Manager C interface exposes only `init`, `run_command`, `run_command_async`, `free_mem` and handle functions; there is no host-callback mechanism other than the completion callback — [bitwarden-c/src/c.rs](https://github.com/bitwarden/sdk-sm/blob/main/crates/bitwarden-c/src/c.rs)
- Event delivery by function pointer: LiveKit's `InitializeRequest` carries "a pointer to the callback function that will be used to send events and async responses" — [ffi.proto](https://github.com/livekit/rust-sdks/blob/main/livekit-ffi/protocol/ffi.proto)

**Error types across the boundary**
- UniFFI maps Rust error enums to foreign exceptions and requires foreign trait methods to return `Result` with "a compatible error type" — [foreign_traits.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/foreign_traits.md)
- JSON designs re-type errors in each wrapper: 1Password Python wraps every core call in `try ... except Exception as e: raise_typed_exception(e)` — [onepassword-sdk-python core.py](https://github.com/1Password/onepassword-sdk-python/blob/main/src/onepassword/core.py)
- Delta Chat's stated reason for JSON-RPC over the C API includes that it "returns better errors than the CFFI" (search summary of its Python docs) — [deltachat-rpc-server on PyPI](https://pypi.org/project/deltachat-rpc-server/)
- Panics must not unwind into the host: Valkey declares callbacks `extern "C-unwind"`; BAML's CFFI has a dedicated `panic` module; Bitwarden's `run_command` still contains `panic!("failed to return command result: null encountered")` — sources in section 1.

**Streaming and pagination**
- UniFFI has no stream type (issues #2755 open, #1485 closed; section 3).
- OpenDAL exposes iterator-like objects per binding instead: `bindings/python/src/lister.rs` and `file.rs`, `bindings/java/src/operator_input_stream.rs` and `operator_output_stream.rs` — [bindings/python/src](https://github.com/apache/opendal/tree/main/bindings/python/src), [bindings/java/src](https://github.com/apache/opendal/tree/main/bindings/java/src)
- Matrix pushes updates through listener callbacks and returns a `TaskHandle` for the subscription (section 1).
- Message-size ceilings appear in JSON designs: 1Password caps messages at 50 MB in Python ("consistent with the other SDKs (where this limit is 64MB)") — [onepassword-sdk-python core.py](https://github.com/1Password/onepassword-sdk-python/blob/main/src/onepassword/core.py)
- The Component Model now has `stream<T>` and `future<T>` in its ABI (WASI 0.3, section 3).

**Cancellation**
- Not carried by UniFFI (section 3); Matrix adds `TaskHandle::cancel()` (abort); Bitwarden's C API adds `abort_and_free_handle(join_handle_ptr)` with an explicit `is_cancellable` flag at call time; napi offers `AbortSignal`; `pyo3-async-runtimes` cancels the Rust future when the asyncio future is cancelled; Go passes `context.Context` (1Password) — sources in sections 1 and 3.

### Inferences
What the precedents imply the Rust core must look like from day one so bindings do not force a redesign:
- Host-implemented extension points (`TokenStore`, optional HTTP transport, event sinks) should be `dyn`-compatible traits held as `Arc<dyn Trait>`, `Send + Sync + 'static`, with owned parameters and return values, a concrete error enum, and async expressed in a form `async-trait` can wrap. A generic `impl TokenStore` parameter or borrowed arguments cannot cross UniFFI, and JSON/C-ABI paths cannot carry a host trait at all without a separate callback protocol.
- The core should never assume an ambient Tokio runtime. It needs either an owned runtime it creates on demand or an explicit handle supplied at construction, because every binding precedent ends up deciding this in the bridge and none relies on the caller being inside `#[tokio::main]`.
- Token refresh must be safe when the store is slow, re-entrant and on another thread: Temporal's thread-affinity problem means a host `TokenStore` in Python or Ruby may only be callable from a host-created thread, so the core should treat store calls as potentially blocking, potentially serialized, and never hold a lock across them.
- Pagination should be cursor-in, page-out at the core's lowest public layer (a `Stream` can be a Rust-only convenience on top), because no generic binding tool carries streams today.
- Cancellation should be an explicit handle or drop-safe futures with no detached background work, so that each bridge can map it to `AbortSignal`, asyncio cancellation, `context.Context` or a `cancel()` method.
- Errors should be one flat, serializable enum with a stable code, message and retryable flag. Rich nested error types and `anyhow` chains do not survive either UniFFI or JSON.
- Public types should avoid lifetimes, generics and trait objects in data positions, and should be `serde`-serializable, so the same types can back a typed UniFFI surface and a JSON surface.

### Gaps
- I did not find a precedent that passes a host-implemented async store through a JSON or C-ABI surface (a reverse call from Rust into the host). Whether Bitwarden's Secrets Manager SDK or 1Password handles token persistence entirely inside the core was not confirmed.
- How Temporal's Python and Ruby bridges solve thread affinity in code (which queue or loop they marshal onto) was not read from source.
- I did not verify how napi-rs surfaces Rust errors as typed JavaScript errors, or how PyO3 projects map error enums to exception classes in OpenDAL.
- Backpressure for streamed results across any of these boundaries was not researched.

## 5. API surface: fully typed per language, or a narrow dynamic surface with generated wrappers?

### Takeaway
Projects that support many languages keep the FFI surface to a handful of functions carrying serialized messages (JSON or protobuf) and put idiomatic, typed wrappers on the host side, usually generated from a schema. Fully typed per-language FFI is what two-to-four-language projects do. Maintainers who comment on it all say the same thing: keep the bridge thin.

### Cited Findings
- Narrow surfaces, as shipped:
  - 1Password: `InitClient`, `Invoke`, `ReleaseClient`, with `Invoke` taking `{ name, parameters }` as JSON, identical across Go (WASM) and Python (UniFFI) — [onepassword-sdk-go core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/core.go), [onepassword-sdk-python core.py](https://github.com/1Password/onepassword-sdk-python/blob/main/src/onepassword/core.py)
  - Bitwarden Secrets Manager: "three FFI functions, `init`, `run_command` and `free_memory`", with a `sdk-schemas` crate in the workspace — [Bitwarden contributing docs](https://contributing.bitwarden.com/architecture/sdk/secrets-manager), [sdk-sm crates/](https://github.com/bitwarden/sdk-sm/tree/main/crates)
  - LiveKit: one request function taking a protobuf `FfiRequest` oneof and returning `FfiResponse`, plus one callback for events — [ffi.proto](https://github.com/livekit/rust-sdks/blob/main/livekit-ffi/protocol/ffi.proto)
  - Temporal: protobuf messages defined as gRPC services; "make it easier to hit the ground running in new languages" — [sdk-core ARCHITECTURE.md](https://github.com/temporalio/sdk-core/blob/master/ARCHITECTURE.md)
  - Delta Chat: JSON-RPC 2.0 with an OpenRPC description and a partly generated TypeScript client; the same API is reachable over stdio or in-process through four C functions — [deltachat-jsonrpc README](https://github.com/chatmail/core/blob/main/deltachat-jsonrpc/README.md)
  - BAML CFFI: `call_function_from_c` with protobuf-encoded arguments and callback by id — [functions.rs](https://github.com/BoundaryML/baml/blob/canary/engine/language_client_cffi/src/ffi/functions.rs)
- Typed surfaces, as shipped: OpenDAL (hand-written classes per binding), LanceDB (PyO3 and napi classes), Matrix and Mozilla (UniFFI objects, records and callback interfaces), Polars — sources in section 1.
- Maintainer guidance on width:
  - Temporal (transcript paraphrase): "In an ideal world, these layers are thin. You don't want a ton of stuff in here"; "Keep the absolute minimum amount of code and logic that you can in these bridges because then you have less opportunities to screw these things up." JSON versus direct object construction was benchmarked and "the performance difference [was] minor in their use case" — [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)
  - LiveKit (raw): "the ffi client is easier to implement if there is less handles to manage" — [ffi.proto](https://github.com/livekit/rust-sdks/blob/main/livekit-ffi/protocol/ffi.proto)
  - iroh-ffi limits bindings to "the stabilized iroh 1.0 surface" and declares the higher-level protocols "out of scope" — [iroh-ffi README](https://github.com/n0-computer/iroh-ffi/blob/main/README.md)
- The cost of serialization at the boundary is what Prisma cites against its own Rust engine: data "must be serialized from JavaScript to Rust and then back to JavaScript, reducing efficiency" — [Prisma blog](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)
- A hybrid exists in one codebase: Bitwarden uses typed UniFFI/wasm-bindgen for its own first-party apps (Kotlin, Swift, TypeScript) and the JSON command surface for the eight third-party-facing languages — [language bindings docs](https://contributing.bitwarden.com/architecture/sdk/language-bindings), [Secrets Manager docs](https://contributing.bitwarden.com/architecture/sdk/secrets-manager)

### Inferences
- For Socket the surface width is decided by the operations, not by the auth layer. A typed FFI class per vendor operation ("send a Slack message", "create a GitHub issue") multiplies by languages and by integrations; no precedent does this. A single `invoke(integration, operation, json) -> json` entry point plus a machine-readable schema per operation is the only shape the multi-language precedents support at that width.
- That shape needs the Rust core to have, beneath the typed Rust clients, a uniform dynamic layer: an operation registry keyed by name, JSON (or protobuf) input and output types with derivable schemas, and an enumerable catalogue. If typed clients are the only layer, a dynamic layer has to be retrofitted before any binding can exist. The OpenDAL `OperatorRegistry` recorded in the packaging note is the same idea applied to backends.
- Schemas also serve the adjacent goals already researched (MCP tool exposure, generated host wrappers), so the dynamic layer is not FFI-only work.
- Serialization overhead that hurt Prisma (tens of thousands of rows per query) is unlikely to matter for SaaS API calls dominated by network latency; Temporal measured it as minor. This is reasoning from those two data points, not a measurement.
- The auth and connection layer is the part worth exposing with real types (connection objects, a host `TokenStore` trait, typed errors), because it is small, stable and stateful, and because that is where Bitwarden and Matrix use UniFFI traits.

### Gaps
- I did not confirm how Bitwarden's or 1Password's typed host wrappers are generated (which schema tool, how much is hand-written).
- No source quantifies bridge code size per language for narrow versus typed designs.
- Whether any project generates idiomatic per-language SDKs for hundreds of operations from schemas on top of a Rust `invoke` core was not found; the nearest are OpenAPI-generated clients talking to a local server (BAML).

## 6. Packaging: Cargo features do not carry over to prebuilt binaries

### Takeaway
Nobody ships Cargo-feature-style selection to npm, PyPI or Maven users. Projects either ship one fat binary per platform with a maintainer-chosen component set (OpenDAL, LanceDB, Polars), or, in one case, a separate prebuilt binary per component (OpenDAL's Go services). A Rust HTTP+TLS client library lands at roughly 3 to 8 MB per platform; cores with more in them are 14 to 85 MB and beyond; the platform matrix is 4 to 11 targets for Node and 4 to 136 wheels for Python.

### Cited Findings

**How optional components are handled**
- One fat binary with a fixed feature set chosen by the binding (raw `Cargo.toml`): OpenDAL's Node and Python bindings define `default` as 14 services (`services-azblob`, `azdls`, `cos`, `fs`, `gcs`, `ghac`, `http`, `ipmfs`, `memory`, `obs`, `oss`, `s3`, `webdav`, `webhdfs`) and a separate `services-all`; the Java and .NET bindings hard-code longer lists in the dependency line. The core crate has 68 `services-*` features — [nodejs/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/nodejs/Cargo.toml), [python/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/python/Cargo.toml), [java/Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/java/Cargo.toml)
- Per-component packages: OpenDAL Go. "Each service is a separate companion module. Add the schemes you use, for example ... `go get github.com/apache/opendal-go-services/memory`". The companion repository "served as the pre-build go binding services release" and contains 8 service directories (aliyun_drive, azblob, fs, gcs, gdrive, memory, oss, s3); each holds a complete compressed C library, for example `s3/libopendal_c.linux.amd64.so.zst` 3,010,197 bytes and `libopendal_c.linux.arm64.so.zst` 2,991,260 bytes, with `embed_linux_amd64.go` / `embed_linux_arm64.go`. The four directories I listed (s3, fs, memory, gcs) contain Linux builds only, at 2.2 to 3.2 MB each — [bindings/go/README.md](https://github.com/apache/opendal/blob/main/bindings/go/README.md), [opendal-go-services](https://github.com/apache/opendal-go-services), [opendal-go-services s3/](https://github.com/apache/opendal-go-services/tree/main/s3)
- Per-variant binary packages behind a pure-Python front: `polars` 2.0.0 is a single `py3-none-any` wheel of 876,611 bytes; the native code ships as `polars-runtime-32`, `polars-runtime-64` and `polars-runtime-compat`, each with 8 `cp310-abi3` wheels of 47.8 to 54.5 MB — [PyPI polars](https://pypi.org/pypi/polars/json), [PyPI polars-runtime-32](https://pypi.org/pypi/polars-runtime-32/json)
- Per-platform packages selected by the installer: npm `optionalDependencies` (OpenDAL 8, BAML 8, nodejs-polars 8, LanceDB 7 native, Statsig 9, Valkey GLIDE 6, iroh 11, Delta Chat's RPC server 10); Maven classifiers (OpenDAL: a 268,765-byte base jar plus 7 classifier jars for linux x86_64/aarch_64 in gnu and musl, osx x86_64/aarch_64, windows x86_64) — [npm opendal](https://registry.npmjs.org/opendal/latest), [npm @statsig/statsig-node-core](https://registry.npmjs.org/@statsig%2Fstatsig-node-core/latest), [npm @number0/iroh](https://registry.npmjs.org/@number0%2Firoh/latest), [Maven opendal 0.50.7](https://repo1.maven.org/maven2/org/apache/opendal/opendal/0.50.7/)
- All platforms in one package: Temporal's `@temporalio/core-bridge` (152 MB unpacked, five binaries). The maintainer's explanation (transcript paraphrase): "For my npm package, every time a user takes a dep, they download all the binaries for every architecture" — [unpkg file listing](https://unpkg.com/@temporalio/core-bridge@1.24.0/?meta), [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)
- Executable in a wheel or npm package (sidecar distribution): `deltachat-rpc-server` 2.62.0 ships 11 `py3-none-<platform>` wheels of 9.7 to 11.7 MB and 10 npm platform packages (`@deltachat/stdio-rpc-server-linux-x64` is 27,481,227 bytes unpacked) — [PyPI deltachat-rpc-server](https://pypi.org/pypi/deltachat-rpc-server/json), [npm @deltachat/stdio-rpc-server](https://registry.npmjs.org/@deltachat%2Fstdio-rpc-server/latest)

### Inferences
- Socket's "enable only the integrations you need" promise cannot be kept for non-Rust users by compile-time features. The realistic options, in order of precedent strength: (a) one binary per platform containing every integration, which works if integrations are thin HTTP code and the binary stays small; (b) a binary containing a curated tier with the long tail absent; (c) per-integration packages each embedding a full copy of the core, as OpenDAL does for Go, which duplicates the core and TLS stack per integration and raises questions about several copies of a runtime in one process; (d) integrations as data or WASM loaded at run time, for which no native precedent exists.
- If integrations are mostly request/response mappings over one shared HTTP client, option (a) is cheap: the size table suggests the HTTP+TLS+runtime base is the bulk of a 3 to 8 MB artifact (Bitwarden, Statsig, obstore, Infisical). I did not verify the dependency stacks of all four, so treat the range as indicative. The 17 to 85 MB OpenDAL artifacts show what happens when each component brings its own vendor SDK dependencies.
- A practical minimum release matrix for "works where developers expect" is about 8 Node targets and, with `abi3`, 7 to 9 Python wheels (27 if supporting pre-abi3 and free-threaded builds), 7 Maven classifiers, and prebuilt static or shared libraries for Go per OS/arch/libc. Each language adds its own publish pipeline and its own class of install-time bug reports.
- OpenDAL versions each binding separately from the core, which means a binding user cannot tell from the version number which core release, and therefore which services and fixes, a given package contains. A project that wants "same integrations in every language" needs to publish that mapping explicitly.

### Gaps
- No source states measured sizes for a minimal `reqwest` + `rustls` + `tokio` addon; the 3 to 8 MB range is read off whole products.
- I did not check whether OpenDAL's Go service modules for non-Linux platforms exist elsewhere, or how two service modules coexist in one process.
- npm weekly-download and size data for several packages could not be fetched because the npm downloads API returned HTTP 429.
- Release-pipeline effort (CI minutes, number of workflows) per language was not measured for any project.
- NuGet packaging for Rust-core libraries (runtime identifiers, native asset layout) was not researched; OpenDAL's .NET binding is unpublished.

## 7. Alternatives: sidecar process and WebAssembly, compared with in-process FFI

### Takeaway
A local sidecar speaking JSON-RPC or HTTP is the cheapest way to reach every language and is in production (Delta Chat, BAML, Prisma's former binary engine), at the cost of a second process to ship and supervise and of credentials crossing an IPC channel. WASM embedding is in production for exactly this kind of SDK at 1Password, gives one artifact for all platforms and works in runtimes that ban native addons, but the general-purpose Component Model route only became async-capable in June 2026 and has two real hosts.

### Cited Findings

| Dimension | In-process FFI | Local sidecar (stdio / HTTP / socket) | WebAssembly |
|---|---|---|---|
| Who does it | OpenDAL, Temporal, Bitwarden, Matrix, Valkey GLIDE, Statsig, LanceDB | Delta Chat (`deltachat-rpc-server`, stdio JSON-RPC); BAML (local HTTP server + OpenAPI clients); Prisma v6 optional binary engine | 1Password Go SDK (Extism); Prisma v7 query compiler (WASM); napi-rs v3 WASM fallback; Matrix and Bitwarden for browsers (wasm-bindgen) |
| Per-language effort | One hand-written bridge per language with a different tool each | A thin RPC client per language; Delta Chat generates its TypeScript client from the RPC definitions and publishes an OpenRPC spec | One host shim per language; needs a WASM runtime in that language |
| Build matrix | Binary per OS/arch/libc per language (4 to 136 artifacts, section 6) | One executable per OS/arch, reused by every language (Delta Chat: 10 npm platform packages, 11 wheels) | One `.wasm` for all platforms (1Password: 9.5 MB) |
| Performance evidence | Prisma chose the in-process library over the sidecar because it "reduces the communication overhead" | Dapr's documented figure for two sidecars on a service call: about 1.40 ms added at p90 and 2.10 ms at p99, 0.48 vCPU and 23 MB per 1,000 requests per second | 1Password's Go core is "single threaded" behind a mutex |
| Constraint evidence | Native addons unsupported on Cloudflare Workers; cgo and JNI "cause a bunch of operational concerns" | A process to spawn and keep alive; Delta Chat ships it as a static binary on `PATH` or inside a package | Component Model hosts today: Wasmtime and jco; async guest support for Python/JS/C# "in-progress" |

Sources: [chatmail/core README](https://github.com/chatmail/core/blob/main/README.md); [deltachat-rpc-server README](https://github.com/chatmail/core/blob/main/deltachat-rpc-server/README.md); [BoundaryML OpenAPI post](https://boundaryml.com/blog/announcing-openapi-support); [Prisma docs, engines (v6)](https://www.prisma.io/docs/orm/v6/more/internals/engines); [Dapr docs, performance (search summary)](https://v1-16.docs.dapr.io/operations/performance-and-scalability/_print); [1Password extism_core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/extism_core.go); [NAPI-RS v3 announcement](https://napi.rs/blog/announce-v3); [Bytecode Alliance, WASI 0.3](https://bytecodealliance.org/articles/WASI-0.3); [InfoQ presentation transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/); [Cloudflare Workers Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)

- Delta Chat offers the same API both ways: the JSON-RPC interface is exposed as "A executable `deltachat-rpc-server` that exposes the JSON-RPC API through stdio" and "can also be called through the C FFI" — [deltachat-jsonrpc README](https://github.com/chatmail/core/blob/main/deltachat-jsonrpc/README.md)
- Delta Chat's reasons for the stdio route: it "doesn't use CFFI layer bindings, which simplifies cross-compilation and reduces binary size", and JSON-RPC "is faster (both to use and to develop) and returns better errors than the CFFI" (search summary of its Python docs) — [deltachat-rpc-server on PyPI](https://pypi.org/project/deltachat-rpc-server/)
- BAML's server keeps execution local: "all 100% local, so you retain control over your prompts and data models" — [BoundaryML OpenAPI post](https://boundaryml.com/blog/announcing-openapi-support)
- Valkey GLIDE shows an in-between design: a Unix domain socket between the host language and the Rust core inside the same process (async Python today), which its Node binding has since replaced with direct calls — [python/glide-async/src/lib.rs](https://github.com/valkey-io/valkey-glide/blob/main/python/glide-async/src/lib.rs), [node/rust-client/src/lib.rs](https://github.com/valkey-io/valkey-glide/blob/main/node/rust-client/src/lib.rs)
- WASM network access is host-mediated and allow-listed in 1Password's design: `AllowedHosts: allowed1PHosts()` in the Extism manifest — [extism_core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/extism_core.go)
- WASM avoids cgo in Go: 1Password's default Go path builds without cgo; only desktop-app integration "requires CGO" — [client_builder_no_cgo.go](https://github.com/1Password/onepassword-sdk-go/blob/main/client_builder_no_cgo.go)
- MCP servers are the same sidecar pattern at ecosystem scale; counts and protocol churn are in the adjacent note `mcp_and_codegen.md` and are not repeated here.

### Inferences
- Effort ranking for Socket's five target ecosystems, from the evidence: sidecar (one binary, five thin clients, possibly generated from the operation schema) is least; WASM is next for languages with an embeddable runtime (Go via wazero/Extism, Node via native WebAssembly or jco, Python via wasmtime-py) and unproven for Java and .NET; in-process FFI is most, with a distinct toolchain per language.
- Credential custody differs in kind. In-process: tokens live in the host's memory and the host's own store implementation is called directly (Bitwarden, Matrix). Sidecar: either the sidecar owns the token store (the host loses custody, which contradicts Socket's "host implements the store" premise) or every token read and write becomes a reverse RPC to the host, which the protocol must be designed for from the start. WASM: the store is a host function, and outbound hosts can be allow-listed, which is a stronger containment story than native code.
- A design that keeps options open is Delta Chat's: define the operation surface once as a JSON-RPC-style protocol, and expose it both in-process (C ABI or UniFFI) and as a stdio/HTTP server. That is compatible with the narrow `invoke` surface in section 5 and lets Socket ship a sidecar first and add in-process bindings per language only where demand justifies the build matrix.
- The Dapr figure is for networked sidecars with mTLS and telemetry; a stdio or Unix-socket sidecar on the same host should cost less, and against SaaS API latencies of tens to hundreds of milliseconds either is small. I found no direct measurement for stdio JSON-RPC.
- Serverless and edge are where the choice bites: a sidecar cannot run on Workers-style platforms and is awkward on function platforms, native addons are banned on some of them, and WASM is the only one of the three that runs everywhere JavaScript does.

### Gaps
- No measured latency for stdio JSON-RPC or Unix-socket IPC against in-process FFI was found for a comparable library.
- I found no production project that embeds a WASI 0.3 component doing `wasi:http` calls inside a Node, Python, Go, Java or .NET application as its SDK core; 1Password uses Extism with core WASM modules, not the Component Model.
- Whether `wasi:http` in Wasmtime and jco supports the connection pooling, proxy and custom-CA behaviour an enterprise integration library needs was not researched.
- How 1Password's JavaScript core performs HTTP (in WASM through fetch, or in JavaScript) was not inspected.
- Supervision patterns for a library-spawned sidecar (crash recovery, version skew between client package and binary) were not researched beyond noting that Delta Chat ships the binary inside the language package.

## 8. Demand side: do Node, Python or Go developers adopt Rust-core libraries for I/O-bound work?

### Takeaway
Yes when the core holds logic that is hard to replicate or delivers a measurable throughput gain (Temporal at 38 million PyPI downloads a month, obstore at 10.9 million, Statsig, 1Password, Valkey GLIDE), and the evidence is weakest, with one clear reversal, for the case closest to Socket: a client that mainly wraps authenticated REST calls. Developers do not appear to choose these libraries because they are Rust; several maintainers report that native extensions are a source of friction.

### Cited Findings
- PyPI downloads, last month (pypistats, read 2026-10-08): `temporalio` 38,050,331; `obstore` 10,920,188; `deltalake` 9,159,509; `lancedb` 7,689,981; `livekit` 5,645,409; `statsig-python-core` 3,556,575; `onepassword-sdk` 3,181,632; `infisicalsdk` (pure Python) 1,532,033; `valkey-glide` 1,212,086; `baml-py` 593,281; `restate-sdk` 292,514; `opendal` 194,771; `bitwarden-sdk` 97,590; `infisical-python` (Rust core, deprecated) 29,628; `deltachat-rpc-server` 17,128 — [pypistats temporalio](https://pypistats.org/api/packages/temporalio/recent), [obstore](https://pypistats.org/api/packages/obstore/recent), [statsig-python-core](https://pypistats.org/api/packages/statsig-python-core/recent), [onepassword-sdk](https://pypistats.org/api/packages/onepassword-sdk/recent), [valkey-glide](https://pypistats.org/api/packages/valkey-glide/recent), [opendal](https://pypistats.org/api/packages/opendal/recent), [infisical-python](https://pypistats.org/api/packages/infisical-python/recent)

- Contributor-side friction: Prisma, "Contributing to the query engine requires a combination of Rust and TypeScript proficiency, reducing the opportunity for community involvement." — [Prisma blog](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)
- The reversal in the nearest category: Infisical replaced its Rust-core SDKs with native ones that call "directly to the Infisical REST API", and the pure-Python replacement now has about 52 times the monthly downloads of the Rust-based package (1,532,033 against 29,628) — [Infisical/ruby-sdk README](https://github.com/Infisical/ruby-sdk/blob/main/README.md), [pypistats infisicalsdk](https://pypistats.org/api/packages/infisicalsdk/recent), [pypistats infisical-python](https://pypistats.org/api/packages/infisical-python/recent)
- OpenDAL, the structural template, has modest non-Rust adoption relative to its Rust standing: 194,771 PyPI downloads a month and 25,891 npm downloads a week — [pypistats opendal](https://pypistats.org/api/packages/opendal/recent), [npm downloads opendal](https://api.npmjs.org/downloads/point/last-week/opendal)

### Inferences
- Download counts measure installs, not preference: Temporal, Statsig, 1Password and LiveKit users install the Rust core because it is the vendor's SDK for a product they already chose. The transferable signal is that a native core does not prevent adoption when the product is wanted, not that developers seek out Rust cores.
- For libraries a developer chooses among alternatives, the Rust-core ones with strong adoption (obstore, deltalake, Polars, pydantic-core) all sell speed. Socket's work is network-bound, so that selling point is unavailable; its selling points would have to be breadth of integrations, correctness of the auth layer and consistency across languages.
- The adjacent research already found that the JavaScript ecosystem has a native-language entrant in this space (Corsair, TypeScript, one plugin package per integration). A Node developer comparing a pure-TypeScript integration library with one that installs a platform-specific native binary has no performance reason to prefer the second, and has the edge-runtime and install-friction reasons above to prefer the first.
- The audience most likely to accept a Rust core for I/O-bound integration work is the one with no good native option and tolerance for native dependencies: Rust itself, and possibly Python backends, where native wheels are routine (cryptography, pydantic-core). Go is the least receptive on the evidence (cgo aversion; three separate projects engineered around it with purego, WASM or a sidecar).
- Taken together with sections 2 and 6, the strategy that fits the evidence is: build the Rust library for Rust users first; design the core so a narrow serialized surface exists; reach other languages initially through a sidecar or MCP-style server built on that surface; add in-process bindings one language at a time only on demonstrated demand, starting where tooling is most mature (Node via napi-rs, Python via PyO3 or UniFFI).

### Gaps
- I found no survey or study of developer attitudes toward Rust-core libraries for I/O-bound work; the evidence is download counts, maintainer statements and one reversal.
- Go module download counts are not public in a comparable form, so Go adoption of Valkey GLIDE, 1Password, Bitwarden and OpenDAL bindings could not be measured.
- npm download counts for `@1password/sdk`, `@bitwarden/sdk-napi`, `@infisical/sdk`, `@slack/web-api`, `@aws-sdk/client-s3` and `@prisma/client` were not retrieved (HTTP 429), so the Node comparison is thinner than the Python one.
- Whether obstore's adoption is driven by measured throughput gains was not verified from its own documentation.
- No integration-library project (as opposed to a vendor SDK) with a Rust core and multi-language bindings was found, so there is no direct demand evidence for Socket's exact category in other languages.
- Maven and NuGet adoption data for Rust-core libraries was not collected.
