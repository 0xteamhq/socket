# Existing embeddable (in-process) open-source libraries offering auth plus operations for many SaaS services, in any language, and the fate of earlier attempts (state as of 2026-10-08)

Notes on method and reliability, for the report writer:

- This note extends `docs/research/notes/non_rust_landscape.md` and `docs/research/notes/rust_ecosystem.md` and does not repeat what they establish. Its purpose was to try to disprove their conclusion ("nothing maintained fills this slot in Rust; closest anywhere is Corsair").
- "GitHub API, 2026-10-08" means the repository was queried directly that day (stars, licence field, language, created/pushed dates, archived flag, directory listings, README and source text). Directory and file counts are raw counts of entries in a folder and can include test files, index files or helper folders; where that matters it is said.
- Registry figures (npm weekly, PyPI monthly, Hex, Packagist, pkg.go.dev) were read from the registries' public APIs or pages on 2026-10-08.
- For `amp-labs/connectors` I shallow-cloned the repository and counted with `grep`; those counts are labelled "grep count" and are approximate to within a few entries.
- Two quotes (Spring Social, Trigger.dev, Redpanda licensing) came through a page-summarising fetch tool; they are presented as quotes from the page but were not read as raw HTML.
- Anything seen only in a search-engine summary is in Gaps, not in Cited Findings.

Headline for the writer: the earlier conclusion survives only in a narrowed form. It missed four things that matter: (1) `amp-labs/connectors`, a maintained MIT Go library that runs in-process with read, write, delete, metadata and webhook-subscription operations over a 251-entry provider catalogue; (2) `superfaceai/one-sdk`, a dormant MIT "one SDK for all APIs" whose core is written in Rust, compiled to WebAssembly and shipped with Node.js, Cloudflare Workers and Python hosts, which is direct prior art for "Rust core plus bindings"; (3) Ballerina's 317 `ballerinax` connector modules (Apache-2.0, in-process, but only inside the Ballerina language); (4) a set of dead or archived libraries of the same shape (Vessel integrations, Spring Social, Trigger.dev v2 integrations). None of them is a maintained, permissively licensed, multi-language library with host-owned credential storage, OAuth flow handling, typed per-service operations and webhooks at breadth.

## 1. Go: `amp-labs/connectors` (Ampersand) in detail, plus Redpanda Connect/Benthos, Steampipe, Conduit and other Go libraries of this shape

### Takeaway
`amp-labs/connectors` is a real, actively developed, MIT-licensed, in-process Go library that the earlier research missed, and it is the closest functional match found outside TypeScript: 251 catalogued providers, generic read/write/delete/metadata/subscribe interfaces, and an HTTP client that refreshes OAuth tokens and calls back to the host when a token changes. It falls short of the described library on OAuth flow orchestration (left to Ampersand's hosted platform), typed per-service functions (operations are generic and keyed by object name), release discipline (no tags or releases) and outside adoption (75 stars, one known importer). The other Go projects are stream or data-pipeline engines whose SaaS connectors are few and, at Redpanda, partly enterprise-licensed.

- LICENSE is the MIT licence with "Copyright (c) 2024 Onset Labs, Inc." — [LICENSE](https://github.com/amp-labs/connectors/blob/main/LICENSE)
- The README describes it as "a Go library that makes it easier to make API calls to SaaS products such as Salesforce and Hubspot. It handles constructing the correct API requests given desired objects and fields." — [README](https://github.com/amp-labs/connectors/blob/main/README.md)
- The README states standalone use is supported and lists what only the hosted platform adds: "It can be either be used as a standalone library, or as a part of the Ampersand platform, which offers additional benefits such as: Handling auth flows; Orchestration of scheduled reads, real-time writes, or bulk writes; Handling API quotas from SaaS APIs; A dashboard for observability and troubleshooting" — [README](https://github.com/amp-labs/connectors/blob/main/README.md)
- The README describes the "Ampersand server" as "a managed service that keeps track of each of your customer's configurations, and makes the appropriate API calls to your customer's SaaS" — [README](https://github.com/amp-labs/connectors/blob/main/README.md)
- Size of the catalogue (shallow clone, 2026-10-08): `providers/` holds 146 sub-directories (per-provider "deep connector" code) and 236 top-level files; there are 251 distinct `SetInfo(<Provider>, ProviderInfo{...})` registrations (grep count) — [providers directory](https://github.com/amp-labs/connectors/tree/main/providers)
- Auth types declared in the catalogue (grep count of `AuthType:` lines, slightly above 251 because some files declare several): 135 `Oauth2`, 69 `ApiKey`, 33 `Basic`, 13 `Custom`, 8 `None` — [providers directory](https://github.com/amp-labs/connectors/tree/main/providers)
- Capability flags set to `true` in the catalogue (grep count of lines in `providers/*.go`): `Proxy` 249, `Read` 196, `Write` 185, `Subscribe` 36, `Delete` 19 — [providers directory](https://github.com/amp-labs/connectors/tree/main/providers)
- A catalogue entry is declarative provider metadata. The Slack entry sets `AuthType: Oauth2`, `BaseURL`, `Oauth2Opts{GrantType: AuthorizationCode, AuthURL, TokenURL, ExplicitScopesRequired, TokenMetadataFields{ScopesField, WorkspaceRefField}}`, a `Support{Proxy, Read, Write, Subscribe, BulkWrite{...}}` block, post-authentication metadata (`teamId`) and a "Webhook Signing Secret" provider-app parameter — [providers/slack.go](https://github.com/amp-labs/connectors/blob/main/providers/slack.go)
- The public interfaces in `connectors.go` are `Connector`, `ProxyConnector`, `URLConnector`, `ReadConnector` (`Read(ctx, ReadParams)`), `WriteConnector` (`Write(ctx, WriteParams)`), `DeleteConnector`, `BatchWriteConnector`, `ObjectMetadataConnector` (`ListObjectMetadata`), `UpsertMetadataConnector`, `DeleteMetadataConnector`, `AuthMetadataConnector` (`GetPostAuthInfo`), `RecordCountConnector`, `BatchRecordReaderConnector`, `WebhookVerifierConnector` (`VerifyWebhookMessage`), `SubscribeConnector` (`Subscribe`, `UpdateSubscription`, `DeleteSubscription`) and `RegisterSubscribeConnector` — [connectors.go](https://github.com/amp-labs/connectors/blob/main/connectors.go)
- Operations are generic and keyed by object name, not typed per service: the standalone example calls `conn.Read(ctx, connectors.ReadParams{ObjectName: "Contact", Fields: connectors.Fields("FirstName", "LastName", "Email")})` and pages with `NextPage` until `result.Done` — [examples/deep_connectors/salesforce/salesforce.go](https://github.com/amp-labs/connectors/blob/main/examples/deep_connectors/salesforce/salesforce.go)
- For Slack the write surface is expressed as API method names used as object names; the connector's create-support test maps `"chat.postMessage"` to its response fields — [providers/slack/support-create_test.go](https://github.com/amp-labs/connectors/blob/main/providers/slack/support-create_test.go)
- Webhook coverage is narrower than read/write: 13 provider directories implement `Subscribe(` and 18 implement `VerifyWebhookMessage(` (grep count) — [providers directory](https://github.com/amp-labs/connectors/tree/main/providers)
- Credential handling is host-supplied. A connector is constructed with `WithAuthenticatedClient(...)`; the OAuth HTTP client is built with options `WithOAuthConfig(*oauth2.Config)`, `WithOAuthToken(*oauth2.Token)`, `WithTokenSource(oauth2.TokenSource)`, `WithTokenUpdated(func(oldToken, newToken *oauth2.Token) error)`, `WithOAuthUnauthorizedHandler(...)`; API-key, basic and custom auth have their own files in `common/` — [common/oauth.go](https://github.com/amp-labs/connectors/blob/main/common/oauth.go), [common directory](https://github.com/amp-labs/connectors/tree/main/common)
- The standalone example starts from an already-obtained access token and refresh token plus the host's own OAuth client id and secret (`OAuth2ClientId`, `OAuth2ClientSecret`, `OAuth2AccessToken`, `OAuth2RefreshToken`), and reads the provider's endpoints from the catalogue with `providers.ReadInfo(providers.Salesforce, ...)` — [examples/deep_connectors/salesforce/salesforce.go](https://github.com/amp-labs/connectors/blob/main/examples/deep_connectors/salesforce/salesforce.go)
- Release discipline: the repository has 0 releases and 0 git tags (GitHub API and `git ls-remote --tags`, 2026-10-08); pkg.go.dev shows only a pseudo-version, `v0.0.0-20261007225344-d00606a71333` — [pkg.go.dev](https://pkg.go.dev/github.com/amp-labs/connectors?tab=importedby)
- Adoption outside the vendor is minimal: pkg.go.dev lists 1 known importer, `github.com/touutae-lab/ampersand-experiment` — [pkg.go.dev importers](https://pkg.go.dev/github.com/amp-labs/connectors?tab=importedby)
- The library depends on the vendor's shared module `amp-labs/amp-common` (MIT, 1 star), and the README instructs contributors to use its `future` and `simultaneously` packages "shared across Ampersand services" — [README](https://github.com/amp-labs/connectors/blob/main/README.md), [amp-labs/amp-common](https://github.com/amp-labs/amp-common)
- Contribution model: contributors need "your own developer account and instance with the provider you're testing", add a `creds.json`, and add a catalogue file `providers/<PROVIDER>.go` for a proxy connector — [CONTRIBUTING.md](https://github.com/amp-labs/connectors/blob/main/CONTRIBUTING.md)
- The `amp-labs` organisation's other public repos are the CLI, React components, docs, an OpenAPI tool, samples and demos, all MIT; no server repository is public (GitHub API, 2026-10-08) — [amp-labs org](https://github.com/amp-labs)

### Inferences
- Ampersand's library is the strongest disproof candidate for "nothing else exists". Measured against the described library it has: permissive licence, in-process execution with no vendor service, host-owned credentials (the host passes tokens in and receives refreshed tokens through a callback), reads, writes, deletes, schema metadata, webhook subscription and verification for a subset, and a 251-entry MIT provider catalogue. That catalogue is also a counter-example to the earlier note's statement that the largest reusable provider-metadata catalogue is Nango's ELv2 file: Ampersand's is smaller (251 against about 1,046) but MIT.
- What it lacks relative to the described library: (a) the OAuth authorisation step (consent redirect, code exchange, connection records) is positioned as a hosted-platform feature, and the standalone example begins from tokens the host already has; (b) no typed per-operation functions such as "send a Slack message", only `Read/Write/Delete` with string object names, a shape that fits CRM-style record sync better than action-style tools; (c) no tagged versions, so consumers pin commit pseudo-versions of a repository receiving roughly 130 commits a month; (d) a single-vendor project whose roadmap follows Ampersand's customers (the provider list is heavy on CRM, sales engagement, support and marketing tools); (e) Go only, with no C ABI or bindings; (f) negligible external use.
- The gap between 75 stars and one known importer on one side and 3,505 commits on the other suggests the library is open-sourced plumbing of a hosted product rather than a community project. This is my reading of the counts.
- Redpanda Connect shows the same licence drift the earlier note recorded for Airbyte: the Salesforce-type connectors that matter to SaaS integration sit behind an enterprise licence. Benthos can be linked into a custom Go binary, but it is a stream engine driven by pipeline configuration, not a callable operations library.
- Go has no Corsair-equivalent (per-service typed operations plus managed OAuth connections as a library). The slot the earlier note called open in Rust is only partly filled in Go.

### Gaps
- I did not find where, if anywhere, the Go library performs the OAuth authorisation-code exchange itself; a grep for `AuthCodeURL` and `.Exchange(` failed for a shell reason and the clone was removed before it was re-run. The README's wording and the example are the only evidence that this step is left to the platform or the host.
- Ampersand's marketing count ("250+ connectors", "241 providers" in a public providers API) was seen only in a search summary of its comparison pages and not opened: [Ampersand vs Nango](https://new.withampersand.com/compare/nango).
- Ampersand's funding, customer count and pricing were not checked.
- Whether Conduit or Benthos document being embedded as a Go library (rather than run as a binary) was not read from their docs in this session.
- Which specific Redpanda Connect connectors are enterprise-only was not listed on the licensing page read; a search summary said Salesforce components are among them: [redpanda.com/connect](https://redpanda.com/connect). The same summary gave "223 Apache 2 Licensed, open source connectors" at the May 2024 Benthos acquisition, from [Introducing Redpanda Connect](https://www.redpanda.com/blog/redpanda-connect), not opened.
- Steampipe's alternative distributions (plugins as Postgres FDW, SQLite extension, standalone exporter) remain unchecked, as in the earlier note.

## 2. Python, JVM, .NET, PHP, Ruby, Elixir and others: libraries of this shape, especially ones with write operations

### Takeaway
Outside Go and TypeScript, the only catalogue-scale in-process libraries with write operations are Apache Camel's SaaS components and Ballerina's 317 `ballerinax` connector modules (both Apache-2.0, both JVM-bound, Ballerina usable only from its own language). Python's catalogues are read-oriented data loaders; .NET, PHP, Ruby and Elixir have multi-provider login libraries and narrow-domain multi-provider libraries (payments, notifications) but nothing combining managed SaaS OAuth connections with per-service operations, apart from Tango, a tiny Elixir OAuth-connection library with no operations.

### Inferences
- Ballerina is the largest non-TypeScript catalogue of typed, write-capable SaaS clients found (317 modules, none archived, vendor-maintained by WSO2), and it runs in-process. It does not weaken the case for the described library much, because the connectors are written in Ballerina and callable only from Ballerina programs on the JVM. It is evidence that a vendor-funded team can keep hundreds of typed connectors alive when they share one language-level client model.
- OpenIntegrations (1C) is a genuine example of the described shape, per-service modules of ready-made unit functions under MIT with shared plumbing, in an ecosystem the earlier research would never have reached. Its example passes the token as a plain argument, which suggests no connection or OAuth lifecycle layer; I did not read further to confirm.
- dlt's "copy the source into your project and expect the user to edit it" is a distinct distribution model worth noting for the report: it sidesteps versioning and long-tail maintenance by handing ownership of each integration to the consumer. It is the same stance LangChain's maintainers reached in May 2026 (earlier note) and Spring Social's lead reached in 2018 (section 5).
- Tango shows the "library-first Nango" idea has occurred to others in 2025-2026 and that Nango's provider catalogue format is being reused as a de facto standard; Nango's ELv2 licence applies to that catalogue, which a permissive library could not simply copy.
- Narrow-domain multi-provider libraries (Apprise 164 services, ActiveMerchant 252 gateways, Omnipay, Libcloud, Shoutrrr) are the long-lived successes of the "one library, many providers" pattern. All of them have a uniform verb set (send a notification, charge a card, start a server), which matches the earlier note's inference from OpenDAL.

### Gaps
- Ballerina: I did not read how `ballerinax` connectors take credentials, whether they refresh OAuth tokens, or how many of the 317 modules are SaaS applications rather than protocols and databases. The WSO2 claim of connector counts on Ballerina Central was not checked.
- Camel: OAuth and token-refresh handling in camel-salesforce, camel-google and camel-box was not read; the earlier note's gap on this stands.
- .NET: one web search and the NuGet search API surfaced no embeddable multi-SaaS operations library, only single-service packages and commercial ADO.NET data connectors. This is absence in a shallow search, not proof.

## 4. Multi-provider OAuth catalogue libraries as precedent for a "provider catalogue"

### Takeaway
Provider catalogues of 50 to 280 entries are common, permissively licensed and heavily downloaded in every major ecosystem, but they are built for login: they return tokens and a user profile and stop there, with no connection store, no refresh scheduling and no API operations. ### Inferences
- A provider catalogue alone is a solved, low-risk component: every ecosystem has one, typically 50 to 280 providers, maintained by a handful of people through pull requests. The described library's catalogue would not be novel. What the login catalogues do not carry is the API-access detail: per-provider scopes for offline access, refresh quirks, base URLs, pagination and rate-limit headers, webhook signing. Only Ampersand's and Nango's catalogues hold that, plus Grant's to a lesser degree.
- The login libraries hand tokens to the host and store nothing, which is "host-owned credentials" by default. The missing piece in all of them is the connection lifecycle: refreshing before expiry, serialising concurrent refreshes, re-authorisation, revocation and per-tenant isolation. Tango (Elixir) and Corsair are the only libraries found that implement that lifecycle in-process, and both require the host's database schema.
- Two packaging patterns appear and both work at this scale: one package with all providers (goth, Arctic, Grant, Assent, social-core, Auth.js, better-auth) and one package per provider (OmniAuth, Passport, Ueberauth, Socialite Providers, aspnet-contrib). Single-package catalogues stay coherent only because each provider is a few dozen lines of configuration. This supports feature-flagged catalogue entries in one crate but says nothing about per-service operations, which are orders of magnitude more code.
- Staleness is handled informally almost everywhere: a disclaimer (league), a recommendation to move to a successor (aspnet-contrib to OpenIddict), or simple abandonment of the catalogue package (loginpass). Passport's core has had no npm release since November 2023 while still drawing about 10 million weekly downloads, which shows that login catalogues tolerate neglect because OAuth endpoints change rarely. API operation catalogues do not have that property, as Spring Social's end-of-life statement says directly (section 5).

### Inferences
- The three written explanations (Spring Social 2018, Trigger.dev v3, LangChain May 2026) come from projects that were not short of users or funding, and they converge: per-service bindings inside a shared library are expensive to keep current, most consumers use a small fraction of each binding, and the maintainers concluded users are better served writing or generating the few calls they need. This is the strongest recurring counter-argument to the described library and it has now been made independently in Java, TypeScript and Python over eight years.
- Spring Social is the cleanest historical analogue of Socket's two layers. Its connection framework (the auth layer) was valuable enough to be absorbed into Spring Security; its API bindings (the operations layer) were judged not worth maintaining. That argues for treating the auth and connection layer as the durable core and the operations layer as the part needing a different maintenance answer (generation from specs, a small curated set, or consumer-owned code as dlt does).
- The venture-backed open-source attempts (Supaglue, Revert, Vessel, Pizzly, Pica, OneGraph, Superface) each lasted roughly one to four years in the open before being archived, absorbed or closed. None left a maintained community fork that I found. The pattern is that the open code was the top of a funnel for a hosted product, and when the company changed direction nobody else carried the integrations.
- Two consolidation events point at the same survivor: Revert joined Ampersand and Pizzly became Nango. The surviving companies are hosted platforms that keep some code open (Ampersand MIT, Nango ELv2) and their catalogues are the largest available.
- A caution on reading this list: "died" mostly means the company moved on, not that the library design failed technically. None of the dead projects was a neutral, non-commercial library, so there is no direct evidence on whether a community-governed one would fare differently. Camel (ASF) and the login catalogues are the only long-lived non-commercial comparables, and they survive.

## 6. Final assessment: the five closest existing open-source matches and exactly what each lacks

### Takeaway
The earlier conclusion is weakened but not overturned: there are now two live close matches rather than one (Corsair in TypeScript and Ampersand's `connectors` in Go), plus a dormant Rust-core precedent (Superface OneSDK), but no maintained project combines permissive licence, in-process execution in a language reachable from others through bindings, host-owned credential storage behind a small interface, built-in OAuth flow handling, typed per-service operations with writes, webhooks, and breadth. The specific combination "Rust core with FFI" has been tried once, under MIT, and was abandoned in beta.

### Inferences

What each of the five lacks relative to the described library:

1. Corsair. Lacks language reach (TypeScript runtime required; other languages get HTTP clients to a running Corsair, not bindings), a storage-agnostic credential interface (it mandates five tables and mirrors API data into them), commercial neutrality (hosted Hub is the recommended path and there is a paid Cloud), release maturity (0.1.x) and any published quality tiering for its 358 packages. It has everything else, including writes and webhooks.
2. amp-labs/connectors. Lacks language reach (Go, no C ABI), the OAuth authorisation flow and connection records (hosted platform), typed unit functions (generic `Read/Write/Delete` by object name suits record sync more than actions), broad webhook support, versioned releases, external adoption and vendor neutrality. It has the permissive licence, in-process execution, host-owned tokens with refresh callback, writes and a 251-entry MIT provider catalogue.
3. Apache Camel. Lacks language reach beyond the JVM, a SaaS-first model (components are message endpoints in a routing engine), multi-tenant end-user OAuth connection management as far as I have read, and breadth in SaaS (around 20 application components). It has the best governance and longevity of anything surveyed.
4. Ballerina connectors. Lack language reach entirely (a separate language), and I could not confirm host-owned credential storage or OAuth lifecycle handling. They have breadth, typed writes, a permissive licence and a funded maintainer.
5. Activepieces pieces. Lack a documented way to run outside the Activepieces engine, host-owned credential storage (the engine holds connections) and language reach. They have the largest permissively licensed catalogue of actions and triggers.

Synthesis for the report:

- Did this sweep disprove the earlier conclusion? Partly. "Closest match anywhere is Corsair" should become "closest matches are Corsair (TypeScript) and Ampersand's connectors (Go)", and the Rust note's "no maintained, adopted direct equivalent exists" still holds but should mention Superface's Rust-core OneSDK as abandoned prior art for the Rust-plus-bindings approach. No project found invalidates the claim that the full combination is unoccupied.
- The unoccupied combination is narrower than it first appears. Each property exists somewhere: in-process and permissive (Corsair, Ampersand, Camel, Ballerina), host-owned tokens (Ampersand, goth, Arcade standalone), a permissive API-access provider catalogue (Ampersand, Grant), a Rust core with multi-language hosts (Superface), full OAuth lifecycle as a library (Tango, Corsair). What is new in the proposal is putting them in one neutral project. That is an integration and governance claim, not a technical novelty claim.
- Language reach through FFI is the one property no live project has. Corsair reaches other languages by HTTP to a running instance; Ampersand does not try. The single attempt at a shared compiled core (Superface) chose WebAssembly hosts over a C ABI and stopped at beta with negligible downloads. I found no stated reason for the stop, so it cannot be attributed to the architecture.
- The history in section 5 bears more on the operations layer than on the auth layer. The auth and connection layer is the part that precedent says survives (Spring Security absorbed it; login catalogues with hundreds of providers run for a decade on little maintenance). The operations layer is the part that maintainers of three large projects walked away from in writing. A plan that depends on hand-maintaining hundreds or thousands of typed operations contradicts that record; a plan built on a durable auth core plus generated or curated operations does not.
- For a consumer like n8n needing hundreds to thousands of integrations, none of the live matches reaches that scale in a reusable form: Corsair has 358 package directories of unverified depth, Ampersand 146 connector directories focused on go-to-market tools. The catalogues that do reach thousands (Pipedream, n8n community nodes, Zapier) are platform-bound or not permissively licensed, as the earlier note established.

### Gaps
- The ranking rests on README, source-layout and registry evidence. I did not install or run any of the five, so "in-process, no vendor service" for Corsair and Ampersand is verified from documentation and example code, not by execution.
- Depth of coverage per provider (how many objects or endpoints each connector supports) was not measured for any project.
- I could not establish host-owned credential handling for Ballerina connectors or standalone execution for Activepieces pieces.
- Ecosystems searched with nothing of this shape found: .NET, PHP, Ruby (beyond login, payment and cloud libraries), Elixir (beyond Tango's auth-only library), Go (beyond Ampersand). Ecosystems not searched: Swift, Kotlin, Dart, C/C++, Scala, Haskell, and enterprise connector stores (MuleSoft, WSO2 Micro Integrator, NiFi, Power Platform).
- A Rust re-check was out of scope; the only new Rust fact here is `superfaceai/one-sdk`, found through the Superface organisation rather than through a crates.io search. Other Rust-core projects distributed only through npm or PyPI could have been missed the same way.
- Funding, team size and commercial status of Corsair, Ampersand and Superface were not researched, so the durability judgements about them are inferences from repository activity.
