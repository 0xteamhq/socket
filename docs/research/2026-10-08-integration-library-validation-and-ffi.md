# Build Socket's core, not its catalogue

Socket is a valid library to build and open source does not already provide it, but the version the evidence supports is narrower than the pitch. As of 2026-10-08 no maintained project in any language combines a permissive licence, in-process execution, host-owned token storage, built-in OAuth flow handling, typed per-service operations, webhooks and reach into other languages through bindings; every one of those properties exists somewhere, and the two closest live matches, Corsair in TypeScript and Ampersand's `connectors` in Go, each lack several of them. The motivating consumer is the wrong one: n8n and its peers treat their catalogues as their moat, run connectors on Node.js under rules that exclude native dependencies, and have never adopted another vendor's connector source, while the teams that demonstrably need this are new engines and agent products that today run Activepieces pieces in a Node sidecar or rent a hosted catalogue. A Rust core with bindings is sound only where the core holds logic that is hard to duplicate (the OAuth lifecycle, refresh under concurrency, pagination, retry, webhook verification); for thin REST wrappers the base rate is Infisical, which abandoned exactly that architecture for native SDKs. "Thousands of integrations with usable operations" is not sustained by any catalogue measured: the tested, vouched-for tier sits near 80 integrations after six years at Airbyte, and headline counts overstate usable breadth by a third to a half. What the evidence does support is an auth and connection core, a declarative provider registry covering hundreds of services, a generic authenticated request for each of them, roughly fifty verified integrations at the head, and a definition format plus live verifier that lets a consumer's coding agent add the rest. Build that in Rust first, give it a narrow serialised `invoke` surface from day one, and reach other languages through a sidecar before paying for in-process bindings.

## Every property exists somewhere; no project combines them

The search behind this report was designed to disprove the conclusion of the earlier landscape report in this project, which held that nothing maintained fills this slot and that the closest match anywhere is Corsair. That conclusion survives only in a narrowed form. The earlier sweep had not searched Go, .NET, Elixir or PHP and looked for Rust projects only on crates.io; the new sweep found a second live close match, a dormant project that used Socket's exact delivery architecture, and a set of dead libraries of the same shape. The table lists the closest candidates and what each lacks against Socket as described.

| Project | Language reach | Licence | What it delivers | What it lacks |
|---|---|---|---|---|
| Corsair | TypeScript; other languages call a running instance over HTTP | Apache-2.0 | Typed per-service operations, webhooks, in-process OAuth lifecycle, 358 package directories | Bindings; a storage-agnostic token store (it mandates its own tables in the host database); neutrality (hosted Hub recommended, paid Cloud); maturity (0.1.x); quality tiers |
| `amp-labs/connectors` | Go only | MIT | In-process calls, host-supplied tokens with a refresh callback, read/write/delete, 251-entry provider catalogue | The OAuth authorisation flow; typed unit operations; broad webhooks; tagged releases; outside adoption |
| Activepieces pieces | TypeScript | MIT | 736 pieces as zero-dependency bundles, about 8,500 action files | OAuth flow, refresh and trigger lifecycle, which stay in the platform; types and a licence file in the published bundles; any support for standalone use |
| Apache Camel | JVM | Apache-2.0 | ASF governance, in-process components | SaaS breadth (about 20 application components); an end-user OAuth connection model |
| Ballerina `ballerinax` | Ballerina only | Apache-2.0 | 317 typed connector modules, vendor-maintained | Any reach outside the Ballerina language |
| Superface OneSDK (dormant) | Rust core compiled to WebAssembly, hosts for Node.js, Cloudflare Workers, Python | MIT | The delivery mechanism Socket proposes | A connection or OAuth lifecycle; releases after 2025-01-31 |

Corsair remains the fullest match and nothing about it changed during this research: **13,455 stars, 358 package directories, about 29,000 weekly npm downloads**, Apache-2.0, one GitHub release, still at 0.1.x ([Corsair](https://github.com/corsairdev/corsair), [npm](https://www.npmjs.com/package/corsair)). It departs from Socket's premise in the credential layer, where it requires a database with five tables and mirrors API data into them, and in neutrality, where it recommends a hosted Hub for OAuth and sells a Cloud runtime ([database doc](https://github.com/corsairdev/corsair/blob/main/docs/concepts/database.mdx), [manual-vs-hub doc](https://github.com/corsairdev/corsair/blob/main/docs/hub/manual-vs-hub.mdx)).

Ampersand's Go library is the find that most weakens the earlier report. It is MIT, runs in the caller's process with no vendor service, and takes credentials from the host: a connector is built from tokens the host already holds, and the host registers a `WithTokenUpdated` callback to persist refreshed ones ([common/oauth.go](https://github.com/amp-labs/connectors/blob/main/common/oauth.go)). Its catalogue registers **251 providers, of which 196 support read, 185 write, 36 webhook subscription and 249 a raw authenticated proxy** ([providers directory](https://github.com/amp-labs/connectors/tree/main/providers)). The earlier report stated that a permissively licensed, compiled, in-process library with a host-supplied credential store "does not exist in any ecosystem surveyed"; that sentence is now false for Go taken property by property, and true only for the full combination. What the library withholds is telling. Its README lists "Handling auth flows" among the benefits of the hosted Ampersand platform, so the standalone example starts from an access token and refresh token obtained elsewhere ([README](https://github.com/amp-labs/connectors/blob/main/README.md)). Operations are generic `Read` and `Write` calls keyed by object name, a shape that suits CRM record sync better than "send a Slack message" ([connectors.go](https://github.com/amp-labs/connectors/blob/main/connectors.go)). The repository has 3,505 commits but no tags, no releases, 75 stars and one known importer, which marks it as the open plumbing of a hosted product and not a community project ([pkg.go.dev](https://pkg.go.dev/github.com/amp-labs/connectors?tab=importedby)). The research did not locate where, if anywhere, the library performs the authorisation-code exchange; the README and the example are the only evidence that it does not.

The earlier report also said the idea had been tried exactly once in Rust, by the `swissknife-*-sdk` crates with about 170 downloads each ([crates.io](https://crates.io/search?q=swissknife)). That needs correcting. **Superface OneSDK had a Rust core, compiled to WebAssembly and shipped to Node.js, Cloudflare Workers and Python under MIT**, and it was missed because it was published to npm and PyPI instead of crates.io ([superfaceai/one-sdk](https://github.com/superfaceai/one-sdk)). Its last releases are betas dated 2025-01-31, its npm package draws 666 downloads a week, and the organisation's newest repositories belong to a payments product ([releases](https://github.com/superfaceai/one-sdk/releases), [npm downloads](https://api.npmjs.org/downloads/point/last-week/@superfaceai/one-sdk), [superfaceai org](https://github.com/superfaceai)). OneSDK is prior art for the delivery mechanism only. Its integration logic was data pulled from a registry and its callers passed security values per call, so it never had the connection lifecycle Socket centres on. No stated reason for the stop was found, so the failure cannot be attributed to the architecture. Within Rust itself the slot stays empty: the one Rust integration platform, Pica, is GPL-3.0 and its README says the community edition is no longer actively maintained ([Pica README](https://github.com/withoneai/pica/blob/main/README.md)).

The auth half of Socket is the half with the most precedent. Multi-provider OAuth catalogues of 50 to 280 entries exist in every major ecosystem under permissive licences, from goth's 74 providers in Go to Socialite Providers' 279 in PHP, and they draw tens of millions of downloads ([goth](https://github.com/markbates/goth), [SocialiteProviders](https://github.com/SocialiteProviders/Providers)). They are built for login: they return a token and stop, with no connection store, no refresh scheduling and no operations. Three catalogues are built for API access instead, and two of them are permissive, which corrects the earlier report's statement that the largest reusable provider catalogue is Nango's ELv2 file: Grant holds 218 entries under MIT and Ampersand 251 under MIT, against Nango's roughly 1,046 under ELv2 ([Grant](https://github.com/simov/grant/blob/master/config/oauth.json), [Nango providers.yaml](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml)). A provider catalogue alone is therefore a solved, low-risk component. The missing piece everywhere is the connection lifecycle as a library: refreshing before expiry, serialising concurrent refreshes, re-authorisation and per-tenant isolation. Only Corsair and Tango, an Elixir library with 341 total downloads, implement it in-process, and both dictate the host's database schema ([Tango](https://github.com/agoodway/tango)).

Everything else that claims breadth is a server the application calls. That includes OpenConnector, an Apache-2.0 "auth gateway connecting 1500+ SaaS providers" with 5,968 stars whose architecture this research did not read beyond its description and which deserves inspection before Socket is positioned ([oomol-lab/open-connector](https://github.com/oomol-lab/open-connector)). The custody model of the hosted vendors carries a demonstrated cost: Composio disclosed in May 2026 that attackers exfiltrated about 5,241 API keys and 5,001 GitHub OAuth tokens ([Composio incident post](https://composio.dev/blog/composio-may-2026-security-incident)).

The graveyard is the part of this picture a founder should read twice. At least twelve projects of Socket's shape have been archived, absorbed or turned into hosted products since 2018, including Vessel's MIT integrations library (91 platforms, auto-refreshing client, typed actions, archived in 2023), Supaglue, and Revert, which the earlier report recorded as merely stale and which in fact joined Ampersand in January 2025 ([Vessel](https://github.com/vesselapi/integrations), [Revert](https://github.com/revertinc/revert)). Three well-resourced projects gave reasons in writing, and they agree. Spring Social's lead wrote that "the Facebook API binding offers roughly 180 distinct operations, even though it'd be rare to find an application that requires more than a half-dozen", that keeping bindings in sync "requires an enormous development and testing effort", and advised developers to "write their own API binding implementations" ([Spring Social end of life](https://spring.io/blog/2018/07/03/spring-social-end-of-life-announcement)). Trigger.dev dropped its integration packages with the line "Just use official SDKs, not integrations" ([Trigger.dev v2 to v3](https://trigger.dev/docs/guides/use-cases/upgrading-from-v2)). LangChain sunset its shared community package in May 2026, adding that "with coding agents, it is often simpler to implement tools directly in application code" ([langchain-community issue #674](https://github.com/langchain-ai/langchain-community/issues/674)). Spring Social is the cleanest analogue of Socket's two layers: its connection framework was valuable enough to be absorbed into Spring Security, and its API bindings were judged not worth maintaining. Two cautions apply to this record. "Died" mostly means the company moved on, since every dead project was the top of a funnel for a hosted product. And no neutral, community-governed library of this shape has been tried, so there is no direct evidence on how one fares; the long-lived non-commercial comparables, Apache Camel and the login catalogues, survive.

## n8n will not consume Socket; newer engines already improvise it

Every workflow platform examined defines a connector as code written against its own runtime, and every one with OAuth splits auth the same way: the connector declares the auth shape and a shared platform layer runs the flow, stores the tokens and refreshes them. n8n is typical. Its first-party catalogue is **308 node directories registering 445 node files and 412 credential classes**, with OAuth handled by a shared package in its core, and the "1500+ integrations" headline is reached by adding community npm packages ([nodes-base package.json](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/package.json), [n8n README](https://github.com/n8n-io/n8n/blob/master/README.md)). The part Socket would replace is therefore a credential service n8n already has, plus per-service declarations n8n has already written.

Whether these platforms could load a Rust-core library is a question of runtime, and the answer is mostly "only through a Node.js binding".

| Platform | Connector runtime | What a Rust core needs | Constraint found |
|---|---|---|---|
| n8n | Node.js | Node binding (native addon or WebAssembly) | Verified community nodes must be MIT with no external dependencies and no file or environment access |
| Activepieces | Node.js | Node binding | Pieces are bundled to one file; native addons stay external |
| Pipedream, Zapier | Node.js on the vendor's infrastructure | Node binding built for the vendor's target | Hosted execution; source-available or proprietary terms |
| Node-RED | Node.js | Node binding | None found |
| Windmill | Rust backend; user scripts in many languages including Rust | Native crate, or TypeScript and Python bindings | None found |
| Kestra | JVM | Java binding | None found |
| Make, Workato | Hosted JSON or Ruby DSL | Not possible in-process; HTTP service only | No native code |

Sources: [n8n verification guidelines](https://docs.n8n.io/integrations/creating-nodes/build/reference/verification-guidelines/), [Activepieces bundling](https://www.activepieces.com/docs/build-pieces/misc/bundling-pieces), [Zapier Platform CLI docs](https://docs.zapier.com/platform/build-cli/overview), [Windmill Rust quickstart](https://www.windmill.dev/docs/getting_started/scripts_quickstart/rust), [Kestra 2.0 plugins](https://kestra.io/blogs/kestra-2-0-plugins).

For the TypeScript platforms a Rust core is a disadvantage. Their authors write TypeScript, their packaging favours pure-JavaScript bundles, and n8n's rule that verified community nodes "not include any external dependencies" excludes a native binding from n8n Cloud; whether a bundled WebAssembly artefact would pass that rule was not established. None of this was tested by loading an addon inside any platform, so the table reflects documented constraints only.

Whether they would consume it is the clearer answer, and it is no. **No workflow platform has adopted another vendor's connector catalogue as its own source**; each writes or crowdsources connectors in its own format, because the catalogue is both the moat and the headline number. What all of them adopted instead is MCP, in both directions: n8n ships four MCP node types, Activepieces exposes every piece as an MCP server, Windmill has an `rmcp`-based crate, and Zapier and Make expose their catalogues as hosted MCP servers ([n8n MCP nodes](https://github.com/n8n-io/n8n/tree/master/packages/%40n8n/nodes-langchain/nodes/mcp), [Activepieces README](https://github.com/activepieces/activepieces/blob/main/README.md), [windmill-mcp Cargo.toml](https://github.com/windmill-labs/windmill/blob/main/backend/windmill-mcp/Cargo.toml)). MCP has not replaced native connectors on the deterministic path, since triggers, typed editor fields and credential UIs still come from native nodes, but it is now the standard answer to "we lack a connector for X". The reverse direction is closed too: n8n's nodes cannot be lifted into another product, because the Sustainable Use License limits use to internal business purposes, every node ships in one 72 MB package with 75 dependencies, and node code runs as a method on a runtime-supplied context ([n8n LICENSE](https://github.com/n8n-io/n8n/blob/master/LICENSE.md), [npm n8n-nodes-base](https://www.npmjs.com/package/n8n-nodes-base)).

The platforms with a real hole are the ones without shared end-user OAuth. Kestra passes tokens as plain task properties, Node-RED handles credentials per node type, and Windmill offers OAuth for a named list of about ten providers ([AbstractGithubTask.java](https://github.com/kestra-io/plugin-github/blob/main/src/main/java/io/kestra/plugin/github/AbstractGithubTask.java), [Windmill integrations](https://www.windmill.dev/docs/integrations/integrations_on_windmill)). Windmill is the best technical fit, since its backend is Rust and already depends on `oauth2`, `reqwest` and `rmcp`, and the weakest commercial fit, since its integration model is "write a script with the vendor's SDK". Kestra has the largest gap but needs a JVM binding, in an ecosystem where Apache Camel already plays the embeddable-component role.

The consumers that exist are downstream of the platforms: products for which integrations are a cost centre. The earlier research classed Activepieces pieces as bound to their engine; that is no longer accurate. Since mid-2026 each `@activepieces/piece-*` package is a zero-dependency single-file bundle, and at least three independent projects load them elsewhere ([npm piece-slack](https://www.npmjs.com/package/@activepieces/piece-slack)). The most instructive is orch8, **a Rust workflow engine that needed connectors and chose to run Activepieces pieces in a Node sidecar over HTTP, passing raw access tokens in the step parameters** ([orch8 activepieces README](https://github.com/orch8-io/engine/blob/main/activepieces/README.md)). It is at once proof of the need, proof that a Rust product had no in-process option, and a description of the incumbent Socket must beat: several hundred MIT pieces available today through a second runtime, with no OAuth or refresh layer. The freepieces project rebuilt that missing layer for Cloudflare Workers, adding its own OAuth flow and encrypted token storage around the same pieces ([freepieces](https://github.com/borgius/freepieces)). These standalone claims rest on project READMEs and tarball contents; the research did not execute a piece outside Activepieces.

Stated demand is absent and revealed demand is present. Searches of Hacker News for an explicit request for an embeddable, self-hosted integration library returned nothing, and Reddit and cross-repository GitHub issues were not searched ([HN Algolia search](https://hn.algolia.com/?q=activepieces+pieces+npm+use+directly)). What exists is a set of teams that each built one layer for themselves: an auth gateway, a typed tool API, a compatibility shim, a sidecar, a TypeScript library. Buyers with money choose hosted catalogues. A Pipedream case study, which the research saw only in a search summary and could not open directly, quotes the agent product Lindy as having spent over $1M building about 250 integrations in two years before switching to a hosted catalogue of 2,500 ([Pipedream blog: Lindy](https://pipedream.com/blog/lindy/)). A library competes for the teams that cannot accept vendor custody of tokens or that ship self-hosted software, and the breadth those teams compare against is thousands, not dozens. The earlier report took its consumer as given, because it treated the library as an extraction for one product. Treated as a standalone project, Socket's first users are Rust and Python backends, new engines and agent builders, and its motivating example is its least likely adopter.

## A Rust core earns its bindings only where logic is hard

The pattern of a Rust core with bindings in several languages is established for network-heavy async libraries: Temporal, Valkey GLIDE, the 1Password and Bitwarden SDKs, LiveKit, Statsig, OpenDAL and Matrix all ship it. The precedents fall into two families, and the difference between them decides Socket's design. Typed-per-language projects cover two to four languages well and stall beyond that. OpenDAL, the structural template for a many-backend library, has **17 binding directories and lists three as released**, each hand-written with a different tool and versioned separately from the core ([OpenDAL bindings README](https://github.com/apache/opendal/blob/main/bindings/README.md)). Message-shaped projects reach five to eight languages by pushing one narrow entry point across the boundary. Bitwarden's Secrets Manager SDK exposes "three FFI functions, `init`, `run_command` and `free_memory`" to eight languages ([Bitwarden docs](https://contributing.bitwarden.com/architecture/sdk/secrets-manager)). 1Password's core interface is `InitClient`, `Invoke` and `ReleaseClient`, with `Invoke` carrying a method name and JSON parameters, identical whether the core is loaded as WebAssembly in Go or as a native library in Python ([onepassword-sdk-go core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/core.go)). Temporal defines its boundary as protobuf messages so that new languages can "hit the ground running", and its maintainers' advice, paraphrased from a conference transcript, is to keep the bridge as thin as possible ([sdk-core ARCHITECTURE.md](https://github.com/temporalio/sdk-core/blob/master/ARCHITECTURE.md), [InfoQ transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)). No precedent exposes hundreds of typed per-vendor operation classes across languages.

The counter-precedents are as informative. Prisma replaced its Rust query engine with TypeScript, citing four costs that map directly onto Socket: contributors need Rust as well as TypeScript, "each operating system and OpenSSL library version needs its own binary", serverless and edge runtimes "aren't always compatible with large Rust binaries", and every call serialises across the boundary ([Prisma blog](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)). Infisical is the nearer case, because its SDK's job was authenticated HTTP calls. It replaced a cross-language Rust SDK with native per-language ones; its Ruby README says the new SDK "talks directly to the Infisical REST API and has no Rust/FFI dependency", and **the pure-Python replacement draws about 52 times the monthly downloads of the Rust-based package it superseded** ([Infisical ruby-sdk README](https://github.com/Infisical/ruby-sdk/blob/main/README.md), [pypistats infisicalsdk](https://pypistats.org/api/packages/infisicalsdk/recent), [pypistats infisical-python](https://pypistats.org/api/packages/infisical-python/recent)). No first-party explanation from Infisical was found, so the motive is inferred from the README wording and the package record. The projects that kept a Rust core have logic that is hard to duplicate correctly: state machines, rule evaluation, cryptography, cluster topology. The ones that left had cores simple enough to rewrite per language. Socket sits between them. OAuth flows, refresh with locking, retry, rate limiting, pagination and webhook verification are moderately complex and worth sharing; "POST a Slack message" is not. If thin operations dominate the library, Infisical's outcome is the base rate.

Demand follows the same line. Developers install Rust-core libraries when the product is wanted or when the core is measurably faster, not because the core is Rust. Temporal's Python SDK has 38 million monthly downloads because it is the vendor's SDK, while OpenDAL, chosen on its own merits, draws about 195,000 a month on PyPI and 26,000 a week on npm ([pypistats temporalio](https://pypistats.org/api/packages/temporalio/recent), [pypistats opendal](https://pypistats.org/api/packages/opendal/recent)). Socket's work is network-bound, so speed is unavailable as a selling point. Go is the least receptive audience: Valkey GLIDE's Go README says cgo with prebuilt static libraries "can make cross-compilation challenging", and three separate projects engineered around cgo with purego, WebAssembly or a sidecar ([valkey-glide go README](https://github.com/valkey-io/valkey-glide/blob/main/go/README.md)).

### The tooling is mature per language and immature as a single answer

Each mainstream target has a production-proven tool for async network code: napi-rs for Node.js, PyO3 with `pyo3-async-runtimes` for Python, UniFFI for Kotlin and Swift, hand-written JNI for Java, and a C ABI with completion callbacks for Go and .NET. No one tool covers Socket's languages. UniFFI's first-party targets are Kotlin, Swift, Python and Ruby, with "3rd party bindings available for C# and Golang" that trail the core by a version and are described by their own authors as young ([uniffi-rs README](https://github.com/mozilla/uniffi-rs/blob/main/README.md), [uniffi-bindgen-go README](https://github.com/NordSecurity/uniffi-bindgen-go/blob/main/README.md)). UniFFI also carries neither cancellation nor streams across the boundary; its manual says to "build your cancellation in a separate, library specific channel" ([UniFFI futures](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/futures.md)). The cost of reaching five languages is therefore five bridges with five toolchains, which Statsig describes from experience: "Plan ahead and know that this can be a painful process. But it's worth it" ([Statsig blog](https://statsig.com/blog/escaping-sdk-maintenance-hell)).

### What the core must look like from day one

The precedents constrain the core's public shape, and retrofitting any of the following means a redesign before the first binding can exist. This section refines the earlier report, which recommended typed per-service clients on shared plumbing as the general layer and pointed to OpenDAL's `impl Future` trait style.

The operation surface needs a uniform dynamic layer beneath the typed Rust clients: a registry of operations keyed by integration and name, JSON-serialisable input and output types with derivable schemas, an enumerable catalogue, and a single `invoke(integration, operation, json) -> json` entry point. This is the only shape the multi-language precedents support at Socket's width, and the same schemas serve MCP tool exposure and generated host wrappers, so the work is not FFI-only. If typed clients are the only layer, every binding multiplies by every integration.

Host-implemented extension points, above all the token store, must be object-safe traits held as `Arc<dyn Trait>`, `Send + Sync`, with owned parameters, `Result` returns and a concrete error type. UniFFI's foreign-trait rules require exactly this, stating that "all parameters must be passed by value" and that every method should return a `Result` ([UniFFI foreign traits](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/foreign_traits.md)). Two production precedents match Socket's token store closely: Bitwarden's async `ClientManagedTokens` trait, implemented in Kotlin, Swift and JavaScript, and Matrix's `ClientSessionDelegate`, which saves and retrieves session tokens through the host's keychain ([Bitwarden auth_tokens.rs](https://github.com/bitwarden/sdk-internal/blob/main/crates/bitwarden-core/src/auth/auth_tokens.rs), [matrix-sdk-ffi client.rs](https://github.com/matrix-org/matrix-rust-sdk/blob/main/bindings/matrix-sdk-ffi/src/client.rs)). A generic `impl TokenStore` parameter or borrowed arguments cannot cross that boundary. Both precedents live on the typed UniFFI and WebAssembly paths; the research found no project that passes a host-implemented async store through a JSON or C-ABI surface, so that reverse-call protocol is Socket's to design.

The remaining requirements follow from how bridges handle async. The core must never assume an ambient Tokio runtime, because every bridge examined creates or receives one explicitly. Token refresh must tolerate a store that is slow, re-entrant and callable only from a host-owned thread, so the core cannot hold a lock across a store call; Temporal's maintainers describe this thread-affinity trap for Ruby, where a callback into host code must run on a thread the host created ([InfoQ transcript](https://www.infoq.com/presentations/rust-polyglot-sdk/)). Pagination must be cursor-in, page-out at the lowest public layer, with Rust streams as a convenience above it. Cancellation must be an explicit handle or drop-safe futures with no detached background work. Errors must be one flat, serialisable enum with a stable code, a message and a retryable flag. Public data types must avoid lifetimes and generics and derive `serde`.

Packaging needs the same early honesty. The earlier report built its developer experience on Cargo features, and that stays correct for Rust users, where per-integration crates behind a facade keep `features = ["slack", "github"]` working. It does not carry over. **Nobody ships Cargo-feature-style selection to npm, PyPI or Maven users**; bindings ship one prebuilt binary per platform with a maintainer-chosen component set, as OpenDAL's Node.js binding does with a default of 14 services ([OpenDAL nodejs Cargo.toml](https://github.com/apache/opendal/blob/main/bindings/nodejs/Cargo.toml)). This favours thin integrations over one shared HTTP client. Rust-core network clients land at roughly 7 to 8 MB per platform, as Bitwarden's and Statsig's Node addons do, while OpenDAL's addon, where components bring their own dependencies, is 85 MB ([npm @bitwarden/sdk-napi-linux-x64-gnu](https://registry.npmjs.org/@bitwarden%2Fsdk-napi-linux-x64-gnu/latest), [npm @opendal/lib-linux-x64-gnu](https://registry.npmjs.org/@opendal%2Flib-linux-x64-gnu/latest)). A realistic release matrix is about eight Node targets, seven to nine Python wheels and seven Maven classifiers, each with its own publish pipeline.

### Sidecar and WebAssembly against in-process bindings

| Dimension | In-process FFI | Local sidecar (stdio or HTTP) | WebAssembly |
|---|---|---|---|
| In production at | OpenDAL, Temporal, Bitwarden, Matrix, Valkey GLIDE | Delta Chat (stdio JSON-RPC), BAML (local HTTP server) | 1Password Go SDK (Extism), napi-rs v3 fallback builds |
| Per-language effort | One hand-written bridge per language, a different tool each | A thin RPC client per language, generatable from the operation schema | One host shim per language; needs an embeddable runtime |
| Build matrix | A binary per OS, architecture and libc, per language | One executable per OS and architecture, reused by every language | One `.wasm` for all platforms (1Password: 9.5 MB) |
| Token custody | Host memory; host store called directly | Sidecar owns the store, or every token read and write becomes a reverse RPC | Store is a host function; outbound hosts can be allow-listed |
| Where it fails | Edge runtimes that ban native addons; cgo and JNI friction | Serverless and edge platforms; a process to supervise | Java and .NET hosts unproven; Component Model hosts are Wasmtime and jco |

Sources: [chatmail/core README](https://github.com/chatmail/core/blob/main/README.md), [BoundaryML OpenAPI post](https://boundaryml.com/blog/announcing-openapi-support), [1Password extism_core.go](https://github.com/1Password/onepassword-sdk-go/blob/main/internal/extism_core.go), [napi-rs v3](https://napi.rs/blog/announce-v3), [Bytecode Alliance WASI 0.3](https://bytecodealliance.org/articles/WASI-0.3).

A sidecar is the cheapest way to reach every language and conflicts most directly with Socket's premise, because either the sidecar holds the tokens or the protocol must carry token-store calls back to the host. WebAssembly is in production for precisely this kind of SDK at 1Password and has the strongest containment story, but the general-purpose Component Model only gained native async and streams with WASI 0.3 in June 2026, and no production project was found embedding a component that makes HTTP calls inside a Node, Python, Go, Java or .NET application. No measurement of stdio JSON-RPC latency against in-process FFI was found; against SaaS API latencies either cost is small, which is reasoning and not a benchmark.

The design that keeps every option open is Delta Chat's: one JSON-RPC-style protocol exposed both as a stdio server and in-process through four C functions ([deltachat-jsonrpc README](https://github.com/chatmail/core/blob/main/deltachat-jsonrpc/README.md)). For Socket that means the strategy is sound in this order: a Rust library for Rust users; a narrow serialised surface in the core; a sidecar and an MCP server built on that surface for every other language; then in-process bindings one language at a time on demonstrated demand, starting with Node.js through napi-rs and Python through PyO3, where tooling is most mature. Committing to five in-process bindings up front is not supported by any project of Socket's size.

## Breadth comes from a registry and a verifier, not hand-written operations

No catalogue measured sustains thousands of working integrations, and the headline numbers shrink on inspection. In Pipedream's repository **1,266 of 3,401 app directories (37%) contain no action and no trigger source**, only an auth definition ([Pipedream components](https://github.com/PipedreamHQ/pipedream/tree/HEAD/components)). In Activepieces, 213 of 736 pieces have three or fewer action files ([Activepieces community pieces](https://github.com/activepieces/activepieces/tree/HEAD/packages/pieces/community)). In Airbyte's registry, 507 of 589 sources are labelled alpha, 81 of 643 connectors are certified, and 54% of rated community sources sit in the lowest sync-success band ([Airbyte OSS registry](https://connectors.airbyte.com/files/registries/v0/oss_registry.json)). The certified share is the honest size of a catalogue, and for Airbyte it is 81 after six years. Supply does not catch demand even at the largest open catalogue: Pipedream has 2,633 open requests for new integrations against 2,189 closed, and its labels record that much of the delay is not code but access, with tags such as `paid-account-needed` and `api-access-not-granted` ([Pipedream issues](https://github.com/PipedreamHQ/pipedream/issues), [Pipedream labels](https://github.com/PipedreamHQ/pipedream/labels)). At n8n the constraint is review capacity: 816 open pull requests against 361 open issues ([n8n pull requests](https://github.com/n8n-io/n8n/pulls)).

Demand is concentrated enough that this matters less than it sounds. Every one of Airbyte's 67 certified sources is rated high-usage, and only 133 of its 589 sources are ([Airbyte OSS registry](https://connectors.airbyte.com/files/registries/v0/oss_registry.json)). Among Activepieces pieces on npm, the top 50 of 735 take 40% of raw downloads ([npm downloads API](https://api.npmjs.org/downloads/point/last-month/@activepieces/piece-slack)); after subtracting a near-uniform floor of about 4,000 monthly downloads per piece that is far more consistent with automated traffic than with human demand, the top 50 hold roughly four-fifths. That adjustment is rough and belongs to the research, not to Activepieces. In public n8n templates, the generic HTTP Request node appears in 3.8 thousand of 7.8 thousand templates and outranks every SaaS integration, which shows what users do when a specific operation is missing ([n8n Pulse](https://n8n-stats.gui.do/nodes)).

### The mechanism: four layers with different economics

A catalogue of hundreds to thousands is achievable only if "integration" means different things at different depths. The first layer is a declarative provider registry for auth, which is the layer with the best scaling record: Nango describes about 1,046 providers with roughly ten auth modes, four of which cover about 87% of entries, and login catalogues run for a decade on little maintenance because OAuth endpoints change rarely ([Nango providers.yaml](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml)). The second is a generic authenticated request for every provider in that registry, the equivalent of n8n's HTTP Request node, Ampersand's `Proxy` capability and the custom API call action Activepieces generates for each piece. The third is a curated head of integrations with typed operations, webhooks and live tests. The fourth is a definition format for operations, interpreted by the core, with an escape hatch for what cannot be declared.

On that fourth layer this report revises the earlier one, which said the evidence for declarative definitions "stops at writes and webhooks". Writes are declarable and in production: n8n's declarative node style and Zapier's request objects both cover them, and Zapier's schema even declares throttling and per-account locking ([n8n node building styles](https://docs.n8n.io/integrations/creating-nodes/plan/choose-node-method), [Zapier schema](https://github.com/zapier/zapier-platform/blob/HEAD/packages/schema/docs/build/schema.md)). The ceiling is lower than the earlier figure implied, though. n8n recommends the declarative style as its default and still has only **about 28 declarative definitions among 308 node directories**, with trigger nodes excluded by design ([n8n nodes-base](https://github.com/n8n-io/n8n/tree/HEAD/packages/nodes-base/nodes)). Of Airbyte's 505 "manifest-only" sources, 53 ship custom Python beside the manifest ([Airbyte connectors directory](https://github.com/airbytehq/airbyte/tree/HEAD/airbyte-integrations/connectors)). Webhook lifecycle (subscribe, renew, unsubscribe) and signature scheme can be declared; payload handling is code in every open catalogue examined. The realistic design is a data-interpreted core with an escape hatch, and the hatch is the real decision: an expression language such as jq or CEL, an embedded script engine, or WebAssembly components, all of which exist as maintained Rust crates ([jaq-core](https://crates.io/crates/jaq-core), [cel](https://crates.io/crates/cel), [wasmtime](https://crates.io/crates/wasmtime)). Interpreted definitions also test more cheaply, since one interpreter suite covers pagination, retry and auth for every definition. No Rust project that interprets a cross-vendor operation catalogue at runtime was found, so this layer has no direct precedent in the language.

### What can be reused, and what cannot

Licences close most shortcuts. n8n's nodes, Pipedream's components, Nango's templates and provider file, and 544 of Airbyte's 589 sources by their own metadata are under source-available licences that bar relicensing; translating them into Socket's format would be preparing a derivative work ([n8n LICENSE](https://github.com/n8n-io/n8n/blob/HEAD/LICENSE.md), [Pipedream LICENSE](https://github.com/PipedreamHQ/pipedream/blob/HEAD/LICENSE), [Nango LICENSE](https://github.com/NangoHQ/nango/blob/HEAD/LICENSE), [Airbyte OSS registry](https://connectors.airbyte.com/files/registries/v0/oss_registry.json)). That reading is of licence text and is not legal advice. Three permissive inputs remain. **Activepieces' 736 community pieces are MIT**, about 8,500 action files and 1,470 trigger files of TypeScript that can be ported with attribution ([Activepieces LICENSE](https://github.com/activepieces/activepieces/blob/HEAD/LICENSE)). Ampersand's and Grant's provider catalogues are MIT. And vendor OpenAPI specifications are mostly permissive: of 26 sampled repositories, 19 carry MIT, Apache-2.0 or BSD licences ([github/rest-api-description](https://github.com/github/rest-api-description)).

OpenAPI coverage is better than the earlier report suggested and less trustworthy than it looks. The earlier picture rested on six vendors. In a convenience sample of 45 well-known products, 28 publish a maintained first-party specification, including GitHub, Stripe, HubSpot, Asana, Intercom, Okta and Microsoft Graph ([HubSpot specs](https://github.com/HubSpot/HubSpot-public-api-spec-collection), [stripe/openapi](https://github.com/stripe/openapi)). The sample is biased upward, and the head of the demand curve is where specs are missing, archived or not REST: Slack's repository was archived in 2021, and no first-party spec repository was located for Salesforce, Notion, Airtable, Zendesk or Shopify. Published specs also drift. The one large measurement found, by a vendor that sells API monitoring and reported through a secondary article, tested 650 million calls and concluded that **75% of production APIs deviated from their published specification** ([Nordic APIs](https://nordicapis.com/most-apis-suffer-from-specification-drift/)). Specs give request and response shapes; pagination style, rate limits and webhook verification are outside the standard. Generation from specs is a credible route to the request layer for a few hundred services and cannot be the quality story.

### AI-generated connectors: authoring is nearly free, owning is not

Agents have collapsed the cost of a first version. Nango reports that its pipeline generated about 200 action and sync functions across five APIs "in 15 minutes for under $20 in token costs", roughly ten cents an operation ([Nango blog](https://nango.dev/blog/using-ai-coding-agents-for-building-api-integrations)). No vendor publishes an acceptance or defect rate. The best independent evidence is Airbyte's public repository, counted for this research: **an AI agent authored 1,192 of the 12,263 pull requests merged in 2026 (9.7%), up from none in 2024, and a deterministic dependency bot authored another 75.9%**, leaving humans about 14% ([Airbyte PRs by Devin](https://github.com/airbytehq/airbyte/pulls?q=is%3Apr+is%3Amerged+author%3Aapp%2Fdevin-ai-integration), [Airbyte PRs by octavia-bot-hoard](https://github.com/airbytehq/airbyte/pulls?q=is%3Apr+is%3Amerged+author%3Aapp%2Foctavia-bot-hoard)). That is the strongest quantitative support for the larger ambition: routine upkeep of a mature catalogue is mostly automatable.

The same data argue against agents growing a catalogue for free. Airbyte's dated catalogue additions fell from 222 in 2024 to 72 in 2025 and 20 in 2026 while agent activity rose, and the registry holds 643 connectors two years after its engineers described a goal of more than 1,000 ([Airbyte OSS registry](https://connectors.airbyte.com/files/registries/v0/oss_registry.json), [Airbyte blog](https://airbyte.com/blog/how-we-test-airbyte-and-marketplace-connectors)). The agent's 25 most recent merged pull requests were 18 documentation changes, 4 bug fixes and one feature. Every one passed human review and CI. The binding constraint is not model capability but a working authenticated connection per provider: Nango states that "an agent that generates code without testing it against the real API will produce code that looks correct but fails in production", and its pipeline has the agent execute against a real connection until tests pass. The only academic benchmark found measured models writing API calls from memory, without the specification, and recorded GPT-4o at 60% correct with hallucinated endpoint URLs in up to 39% of cases for some models, on exactly the APIs Socket would target ([arXiv 2509.20172](https://arxiv.org/html/2509.20172v7)). It is a lower bound for unverified generation, not a measure of a 2026 agent that reads documentation and iterates.

The largest hole in this evidence is on both sides of the central question. No independent practitioner account with production data on agent-written integrations was found, and every qualitative source arguing that agents cannot replace integration infrastructure sells integration infrastructure. The structural argument stands regardless. Agents raise the value of a shared core and lower the value of a shared catalogue of hand-written operations. Given a provider registry, an authenticated client with pagination and retry built in, and a dry-run verifier, an agent produces a working operation in minutes; without them it reproduces the benchmark's failure modes. Nango, StackOne and Airbyte have each built that agent-facing toolchain on top of their own runtime.

### Maintenance and testing costs concentrate at the head

Upkeep follows usage and API complexity, not catalogue size. In Airbyte's registry, **55 of 81 certified connectors (68%) have shipped at least one breaking release against 54 of 562 community connectors (10%)**, and the most-broken are Shopify, Amazon Ads, LinkedIn Ads, Jira, Google Ads and Facebook Marketing. Certified connectors average about 0.4 breaking releases a year each. The low community figure is under-detection as much as stability, since nobody notices when an unused connector breaks. Per-connector cost figures exist only as vendor claims in the range of 300 to 430 hours a year, which describe in-house enterprise integrations with support attached and are an upper bound for a library ([Truto](https://truto.one/blog/the-true-cost-of-maintaining-20-saas-integrations-a-worked-tco-example/)). At the other end, Activepieces' most common cash bounty for a contributed piece was $100 ([Activepieces labels](https://github.com/activepieces/activepieces/labels)).

Nobody tests a large catalogue without live credentials for the part they vouch for; they shrink the vouched-for part. Airbyte's engineers wrote that "it does not scale for Airbyte to maintain a pool of sandboxes seeded with test data for all our connectors" and that test requirements grow with usage ([Airbyte blog](https://airbyte.com/blog/how-we-test-airbyte-and-marketplace-connectors)). Recorded fixtures are the workable default for credential-free CI: Nango regenerates about 7,000 test files from snapshots recorded against real connections, with the weakness that fixtures prove conformance only as of recording day and leak data unless scrubbed ([Nango integration-templates](https://github.com/NangoHQ/integration-templates)). Airbyte leans on production telemetry for its long tail, which a library does not have. Socket's substitute is scheduled live runs where someone sponsors credentials, as OpenDAL does for its S3 tests, and an explicit "fixtures only, last recorded on this date" label for everything else ([OpenDAL aws_s3 action](https://github.com/apache/opendal/blob/main/.github/services/s3/aws_s3/action.yml)). The tier boundary every catalogue converges on is the kind of test an integration has.

## Verdict: valid as an auth-first core, with five risks that decide it

Socket is valid. The combination it proposes is unoccupied, the need is demonstrated by teams improvising it, the custody argument against hosted vendors is concrete, and the Rust slot in particular is empty. The novelty is an integration and governance claim, not a technical one: every component has a working precedent, and what has never existed is a neutral, permissively licensed project that assembles them with host-owned credentials and verification evidence.

The scope the evidence supports has a durable centre and a deliberately thin edge. The centre is the connection and authorisation layer: provider registry, OAuth flows, refresh with locking, a host-implemented token store, an authenticated HTTP client with pagination, retry and rate-limit handling, and multi-provider webhook verification. Precedent says this layer survives; Spring Security absorbed its equivalent while the bindings beside it were abandoned. Around it sits a generic authenticated request for every registered provider, about fifty integrations with typed operations and live conformance tests, a definition format with a verifier that consumers and their agents use to add or repair operations, and an MCP surface in both directions. "Hundreds of providers you can authenticate and call" is an honest claim for that design. "Thousands of integrations with all their operations, maintained by the project" contradicts every catalogue measured and the written experience of three large projects.

This verdict departs from the earlier landscape report in substance, not only in framing. That report treated the library as an extraction for one product, recommended a few dozen hand-written integrations and built its developer experience on Cargo features. The standalone view changes four things. The closest-match claim widens from Corsair alone to Corsair and Ampersand's Go library, with Superface as abandoned prior art for the Rust-core delivery. The scope gains a mechanism for breadth that the earlier report lacked, because declarative operations do cover writes and because agent pipelines with live verification are now measurable. The core's first public design must put an object-safe, serialisable, dynamically invocable layer beneath the typed clients, which the earlier trait advice did not require. And the assumed consumer changes: the earlier report's recommendation to treat MCP as a feature that buys breadth still holds, but the nearest substitute a Rust team reaches for today is an Activepieces sidecar, and Socket has to beat it on token custody, refresh, typed operations and webhooks for a narrow set of services before breadth matters.

Five risks decide the outcome. The first is the operations layer: per-service bindings are the part maintainers of Spring Social, Trigger.dev and LangChain walked away from, and a plan that hand-maintains them at scale repeats that history. The second is the Infisical outcome: if the shared core is thin relative to the operations, bindings cost more in binaries, build matrices and contributor friction than they save, and TypeScript consumers have Corsair with no native dependency. The third is consumer mismatch: the incumbents named in the pitch will not adopt, stated demand was not found in a limited search, and buyers with budgets choose hosted catalogues of thousands. The fourth is credentials: live verification needs a working account per provider, bring-your-own OAuth apps push registration to every consumer, and nobody has published what sandbox upkeep costs. The fifth is durability and trust: every dead predecessor was a commercial funnel that lost its sponsor, a neutral project has no hosted product to fund maintenance, and contributed integration code runs in-process with decrypted tokens, the property attackers exploited with malicious packages posing as n8n community nodes in January 2026 ([Endor Labs](https://www.endorlabs.com/learn/n8mare-on-auth-street-supply-chain-attack-targets-n8n-ecosystem)).

Several facts that bear on these risks remain unknown. OpenConnector's architecture was not read. None of the closest libraries was installed and run, so their in-process claims rest on documentation and example code. Coverage depth per provider was not measured for any project. Why Superface stopped is unstated. And no data exists, in either direction, on how agent-written integrations behave in production.

## Conclusion

The evidence inverts the pitch. Socket was framed as a catalogue with an auth layer underneath; what survives scrutiny is an auth layer with a catalogue as its by-product. Coding agents sharpen that inversion: they have made the operation the cheapest artefact in the system and the verified connection the scarcest, so the asset worth building is the substrate an agent writes against. The registry, the authenticated client, the definition format and the dry-run verifier are the product, and the fifty tested integrations are its proof.

Two inexpensive tests would settle most of what this research could not. The first is whether a consumer shaped like orch8 can replace its Node sidecar with Socket for ten services and gain refresh, token custody and webhooks in the exchange; if it cannot, the incumbent to beat is already good enough. The second is whether the `invoke` surface, exposed through a sidecar, satisfies a Node.js or Python consumer without an in-process binding; if it does, the most expensive part of the strategy can wait for demand to pay for it. Governance is the remaining open question and the only one with no precedent to borrow: every predecessor was a company, and whether a neutral project can hold a verified head catalogue together is something Socket would be the first to find out.
