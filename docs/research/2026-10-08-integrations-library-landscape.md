# No Rust integrations library exists: extract yours

No maintained library in Rust lets you opt into SaaS integrations by Cargo feature from one repository, and no project in any language delivers "thousands of integrations with all their features" as an embeddable library. The only Rust attempt at the idea, the `swissknife-*-sdk` family, was published once in December 2025, has about 170 downloads per crate, and its source repository now returns 404 ([crates.io](https://crates.io/search?q=swissknife)). The closest working match anywhere is Corsair, a twelve-month-old TypeScript library with 13,422 stars, which shows the demand is real ([Corsair](https://github.com/corsairdev/corsair)). You should build this, but as an extraction of your existing private `connector` crate, scoped to a few dozen deep integrations and not to thousands. Every catalogue that reached the hundreds either runs as a hosted service, is generated from one vendor's own specifications, or decayed into an unmaintained long tail. Split the crate at extraction into a small core, one crate per integration and a facade that keeps the `features = ["slack", "github"]` experience. Treat MCP as one more feature that buys breadth, and hand-write the integrations your product needs. The name `link` is taken on crates.io, and so is `connector`.

## The Rust slot is empty, and the one attempt has about 170 downloads

The idea has been tried exactly once in Rust. A crates.io search returns **24 `swissknife-<category>-sdk` crates**, all at version 0.1.1 and all last updated 2025-12-24, with per-provider features such as `asana, clickup, jira, linear, trello` in the project-management crate ([swissknife-pm-sdk](https://crates.io/crates/swissknife-pm-sdk)). An umbrella `swissknife-ai-sdk` adds about 130 feature flags and a `ToolRegistry`, with 0% documentation coverage ([docs.rs](https://docs.rs/swissknife-ai-sdk/0.1.1/swissknife_ai_sdk/)). The published tarball for five project-management providers is 12,908 bytes, so coverage per provider is a few kilobytes of source. It is prior art for the layout, and it shows that a long feature list with shallow coverage earns no users. Its source could not be read, so its trait design is unknown.

Everything else in Rust is a different shape. Oxide's `third-party-api-clients` holds 21 clients generated from OpenAPI specs, published as unrelated crates (`octorust`, `slack-chat-api`, `dolladollabills`) with no shared trait or auth ([GitHub](https://github.com/oxidecomputer/third-party-api-clients)). Pica, the one integration platform written in Rust, is GPL-3.0, needs MongoDB and Redis, and its README says the community edition "is no longer actively maintained" after the company moved to a private cloud ([Pica README](https://github.com/withoneai/pica/blob/main/README.md)). Its open seed data holds 15 connection definitions against a hosted claim of 200 or more, so the valuable definitions were never opened ([seed data](https://github.com/withoneai/pica/blob/main/core/resources/seed/connection-definitions.bson)). No unified-API or agent-tooling vendor ships a Rust SDK: Composio's repository contains only TypeScript and Python, and the only general-purpose Composio client crate is a community one with 87 downloads ([ComposioHQ/composio](https://github.com/ComposioHQ/composio), [composio-sdk](https://crates.io/crates/composio-sdk)). Demand for the pattern is showing up inside applications instead: the agent runtime zeroclaw (32,943 stars) gates about 38 `channel-*` integrations behind Cargo features, which leaves nothing reusable behind ([zeroclaw Cargo.toml](https://github.com/zeroclaw-labs/zeroclaw/blob/main/Cargo.toml)).

The per-service crates explain why people keep rewriting integrations. GitHub, Slack and Stripe have strong community clients: `octocrab` at 18.1M downloads, `slack-morphism` at 5.5M, `async-stripe` at 5.6M ([octocrab](https://crates.io/crates/octocrab), [slack-morphism](https://crates.io/crates/slack-morphism), [async-stripe](https://crates.io/crates/async-stripe)). The business tools are weak. Notion has five competing crates, and the repository of the most recently released one is archived. Linear's best option is a three-month-old crate with 521 downloads. Salesforce's main crate last released in May 2022 ([notionrs](https://github.com/46ki75/notionrs), [linear-api](https://crates.io/crates/linear-api), [rustforce](https://crates.io/crates/rustforce)). Almost none are vendor-official, and the strong ones disagree on HTTP stack and TLS feature names, so a library that re-exports them inherits several dependency trees and cannot offer one auth or retry layer.

Two limits on this finding: the search relied on crates.io and GitHub keyword queries, so an obscurely named crate could have been missed, and Go, .NET, Elixir and PHP were not searched for equivalents.

## Elsewhere the shape exists only as hosted services and one young TypeScript library

Corsair is the proof that the shape works. It is Apache-2.0, ships each integration as its own npm package (`@corsair-dev/slack`), and is configured as `createCorsair({ plugins: [github(), slack()], database, kek })` ([Corsair README](https://github.com/corsairdev/corsair/blob/main/packages/corsair/README.md)). It reached **358 package directories and about 29,000 weekly npm downloads within twelve months** of its first commit ([npm](https://www.npmjs.com/package/corsair)). It departs from a pure library in three ways: it requires a database with five tables and mirrors every API call into it, it recommends a hosted Hub for OAuth, and it sells a Cloud runtime ([database doc](https://github.com/corsairdev/corsair/blob/main/docs/concepts/database.mdx), [manual-vs-hub doc](https://github.com/corsairdev/corsair/blob/main/docs/hub/manual-vs-hub.mdx)). Apache Camel has matched the packaging model in Java for years, with 416 components in 340 separately installable JARs under Apache-2.0, but it models message endpoints, not typed SaaS resources with end-user OAuth ([Camel components](https://camel.apache.org/components/next/index.html)).

Every other large catalogue is a server. The agent-tool vendors claim between 100 and 9,000 apps, and all of them execute tools on a hosted or self-hosted runtime that holds the credentials. Their counts are not comparable, since Composio counts toolkits, Arcade counts tools and Zapier counts apps and actions separately ([Composio pricing](https://composio.dev/pricing), [Arcade docs](https://docs.arcade.dev/en/home), [Zapier MCP](https://zapier.com/mcp)). That custody model has a cost: Composio disclosed on 2026-05-21 that attackers exfiltrated about 5,241 API keys and 5,001 GitHub OAuth tokens ([Composio incident post](https://composio.dev/blog/composio-may-2026-security-incident)).

Openness in this category narrows over time. Airbyte's connectors went from MIT to ELv2, Nango is ELv2 with self-hosting now on its Enterprise plan, n8n and Pipedream are source-available with commercial-use restrictions, and Pica closed its source ([Airbyte licenses](https://docs.airbyte.com/community/licenses), [Nango self-hosting doc](https://github.com/NangoHQ/nango/blob/master/docs/guides/platform/self-hosting/self-hosting.mdx), [n8n LICENSE](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)). Earlier open-source unified APIs did not survive: Supaglue is archived and Revert has not been pushed since April 2025 ([Supaglue](https://github.com/supaglue-labs/supaglue), [Revert](https://github.com/revertinc/revert)). A permissively licensed, compiled, in-process library with no hosted upsell and a host-supplied credential store does not exist in any ecosystem surveyed.

The strongest argument against building comes from LangChain. It sunset `langchain-community` on 2026-05-22 because a shared package with integrations of "widely varying levels of usage, maintenance, and maturity" and a shared release cycle could not be kept at consistent quality, and it added that "with coding agents, it is often simpler to implement tools directly in application code" and that MCP now carries much of the demand ([langchain-community issue #674](https://github.com/langchain-ai/langchain-community/issues/674)). That argument defeats a community-owned monolith of hundreds of integrations. It does not defeat a small, owner-maintained set with per-integration packages, which is what LangChain itself kept in the form of 16 partner packages ([libs/partners](https://github.com/langchain-ai/langchain/tree/master/libs/partners)).

## MCP covers agent tool calls for the big vendors, not webhooks, sync or credential custody

MCP is the main indirect competitor and you should build on it instead of around it. Slack, GitHub, Linear, Notion, Atlassian, Stripe, Salesforce and Google all run official hosted MCP servers with OAuth ([Slack changelog](https://docs.slack.dev/changelog/2026/02/17/slack-mcp/), [Linear MCP docs](https://linear.app/docs/mcp), [Atlassian MCP server](https://github.com/atlassian/atlassian-mcp-server), [Salesforce blog](https://developer.salesforce.com/blogs/2026/04/salesforce-hosted-mcp-servers-are-now-generally-available)). The official Rust SDK `rmcp` is Tier 1 and has **17.9M downloads in the last 90 days**, so MCP is already how Rust agent code reaches SaaS tools ([rmcp](https://crates.io/crates/rmcp), [MCP SDKs](https://modelcontextprotocol.io/docs/sdk)). For interactive, user-delegated, model-driven tool calls against the top vendors, a native client adds little.

The registry's size overstates what is usable. Of roughly 30,375 registered servers in September 2026, 62% have exactly one published version, and the registry records no security review ([registry analysis](https://dev.to/amareswer/the-mcp-registry-by-the-numbers-38nc)). Vendor-official remote servers number in the dozens: Nango's catalogue wires up 36 MCP-auth providers out of about 1,046 ([providers.yaml](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml)). An academic study of 1,899 open-source servers found 5.5% with tool-poisoning vulnerabilities ([arXiv 2506.13538](https://arxiv.org/abs/2506.13538)).

MCP also leaves a backend-shaped hole. The 2026-07-28 revision has no webhook or events primitive, and the events work is a draft extension with one major client implementing a subset capped at 256 KiB with no replay ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)). The protocol defines how a client gets a token, not where a multi-tenant backend stores and refreshes thousands of them. It has no incremental sync contract and no compile-time types. Those four gaps (inbound events, sync, typed operations, credential custody) are the library's functional territory. Whether vendor MCP servers support service-account auth for backend use was not established.

The practical relationship has two directions. Outbound, add a single `mcp` feature that wraps `rmcp`'s client, streamable-HTTP transport and `auth` features, which reaches any vendor's remote server without per-vendor code ([rmcp Cargo.toml](https://github.com/modelcontextprotocol/rust-sdk/blob/main/crates/rmcp/Cargo.toml)). Wrap its types and do not re-export them: `rmcp` shipped 2.0.0 on 2026-06-29 and 3.0.0 on 2026-07-28, and the spec revision it tracks removed sessions and the handshake ([rust-sdk releases](https://github.com/modelcontextprotocol/rust-sdk/releases)). Inbound, derive tool definitions from your typed operations so the same code serves a backend caller, an in-process agent and an MCP server. That second direction is your product's empty tool registry: build it as a thin layer over the typed clients, and the registry becomes a by-product of the library instead of a separate integration effort.

## Split into core, per-integration crates and a facade while the crate has no users

Your existing crate uses the single-crate, feature-per-integration model. That model is not blocked at your size: crates.io caps a crate at **300 features, 500 dependencies and 10 MB**, and you have about 17 integration features ([publish_limits.rs](https://github.com/rust-lang/crates.io/blob/main/src/config/publish_limits.rs)). Apache OpenDAL ran it to 63 services before abandoning it ([opendal 0.55.0](https://crates.io/crates/opendal/0.55.0)). The reason to move now is that the move only gets more expensive, and extraction is already a breaking change with no external users to break.

| Option | Ceiling | Who uses it | Cost observed |
|---|---|---|---|
| One crate, one feature per integration | 300 features; one version and one docs.rs build for everything | OpenDAL until 0.55; generated bindings holding exemptions (`web-sys`, `windows`) | OpenDAL left it at about 65 services; Vector reports single-component builds about 4x faster than all-features |
| Core + crate per integration + facade with features | Facade limited to 300 features and 500 dependencies | OpenDAL since 0.56, `sqlx` since 0.7 | More release coordination; `sqlx` lost trait impls in the split |
| Separate crates, shared runtime, no facade | None in aggregate | AWS (437 service crates), Google Cloud, Azure | Needs release automation and a stable 1.x core |

Sources: [OpenDAL RFC 6828](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/6828_core.md), [vector DEVELOPING.md](https://github.com/vectordotdev/vector/blob/master/docs/DEVELOPING.md), [sqlx CHANGELOG](https://github.com/launchbadge/sqlx/blob/main/CHANGELOG.md), [smithy-rs FAQ](https://github.com/smithy-lang/smithy-rs/blob/main/design/src/faq.md), [aws-sdk-rust](https://github.com/awslabs/aws-sdk-rust/tree/main/sdk).

OpenDAL is the template for the middle row. Its split ran from an RFC on 2025-11-27 to a shipped facade on 2026-05-01, and users kept typing the same thing: each feature became a dependency switch, `services-s3 = ["dep:opendal-service-s3"]` ([opendal 0.59.4](https://crates.io/crates/opendal/0.59.4)). The developer experience you want does not require the single-crate design. `sqlx` shows the risk of waiting: its 0.7 split deleted `Executor` impls that "cannot exist in the new crate architecture without rewriting the `Executor` trait entirely" ([sqlx CHANGELOG](https://github.com/launchbadge/sqlx/blob/main/CHANGELOG.md)). Traits designed inside a monolith do not survive crate boundaries unchanged, so the first public trait design should be written across them.

The split also fixes semver coupling. In one crate, a breaking change in one vendor's surface forces a major bump for users who never enabled that feature. Per-integration crates make tiering, ownership, deprecation and yanking mechanical. Release in lockstep at first, as OpenDAL still does with every crate at 0.59.4 ([opendal-service-s3](https://crates.io/crates/opendal-service-s3)). Independent versions only pay off once the core is 1.x-stable, which is the condition AWS, Google and Azure all meet. No published before-and-after compile-time measurement of such a split was found, so the build-time benefit is argued from structure.

### What the core should and should not contain

OpenDAL succeeds with one backend trait because storage has one narrow verb set. SaaS tools do not share one, which is the likely reason no SaaS equivalent emerged. The shared core should therefore be plumbing: credentials and a host-implemented token-store trait, one HTTP stack, pagination, retry and rate-limit semantics, an error type that separates kind from temporary-or-permanent status, and one capability query ([OpenDAL error.rs](https://github.com/apache/opendal/blob/main/core/core/src/types/error.rs), [OpenDAL RFC 7700](https://github.com/apache/opendal/blob/main/core/core/src/docs/rfcs/7700_capability_api.md)). The generic layers already exist as mature permissive crates: `oauth2` (55.9M downloads), `reqwest-middleware`, `backon`, `governor` ([oauth2](https://crates.io/crates/oauth2), [reqwest-middleware](https://crates.io/crates/reqwest-middleware), [backon](https://crates.io/crates/backon)). What no crate supplies is the provider-specific knowledge: authorize and token URLs, scopes, refresh quirks, pagination style and webhook signing scheme per service. Your OAuth module with definitions for six providers is that asset in miniature. Multi-provider webhook verification is equally unoccupied; the two crates that attempt it have under 700 downloads each ([webhook-verify](https://crates.io/crates/webhook-verify)).

Three implications follow for the extraction, each an inference from the crate description and not from its code. First, your source, signal, harness and sync traits describe roles in your product; the research supports typed per-service clients on shared plumbing as the general layer, with role traits as an optional layer above. Second, the features named `claude-code`, `openai`, `gemini`, `aider` and `acp` are agent harnesses by name, not SaaS integrations, and belong outside a general integrations library. Third, the dependency must point one way: the library must not depend on Cognis, and a separate bridge crate should adapt its operations into Cognis tools, the way Rig ships `rig-rmcp` ([rig crates](https://github.com/0xPlaygrounds/rig/tree/main/crates)). Corsair draws the server boundary cleanly: the library owns provider metadata, token exchange, refresh and encrypted storage, and the host application owns the callback route ([manual-vs-hub doc](https://github.com/corsairdev/corsair/blob/main/docs/hub/manual-vs-hub.mdx)).

## Hand-write a dozen deep integrations, declare the auth catalogue, generate where specs exist

No one hand-writes hundreds of clients. AWS's 437 service crates are generated from Smithy models that one owner controls, and Azure's more curated Rust SDK reached general availability with six service libraries ([aws-sdk-rust](https://github.com/awslabs/aws-sdk-rust/tree/main/sdk), [Azure SDK blog](https://devblogs.microsoft.com/azure-sdk/from-beta-to-stable-announcing-the-azure-sdk-for-rust-ga/)). Cross-vendor SaaS has no uniform specification to generate from. GitHub (1,232 operations), Stripe and Jira publish maintained OpenAPI specs, but Slack's spec repository was archived in 2021 and Linear is GraphQL ([github/rest-api-description](https://github.com/github/rest-api-description), [slack-api-specs](https://github.com/slackapi/slack-api-specs)). The public spec commons, APIs.guru, has no entry updated after 2023 ([APIs.guru list](https://api.apis.guru/v2/list.json)). The realistic Rust generator is `progenitor`, which handles OpenAPI 3.0.x only, leaves auth manual and warns it "may fail for some OpenAPI documents" ([progenitor README](https://github.com/oxidecomputer/progenitor/blob/main/README.md)). It is MPL-2.0, so check how its generated output and runtime are licensed before a permissive crate depends on them. `octocrab` thrives beside GitHub's own spec, which says developers prefer curated APIs to raw generated ones.

Declarative definitions scale for a narrower job than yours. In Airbyte's registry **505 of 589 source connectors are manifest-only YAML, and none of its 54 destinations are** ([Airbyte OSS registry](https://connectors.airbyte.com/files/registries/v0/oss_registry.json)). Declaration works for reading records; the evidence stops at writes and webhooks. Auth is the layer that declares well: Nango describes about 1,046 providers with roughly ten auth modes, and four modes cover about 87% of entries ([providers.yaml](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml)). Nango's repository is ELv2, so write your own catalogue instead of importing theirs.

The scope that follows has three layers. Hand-write deep, typed clients with webhooks for the integrations your product uses, generating a low-level layer where a vendor spec exists. Ship a data-driven provider registry for auth that can cover far more services than you have clients for. Offer the `mcp` feature for everything else. "Thousands with all features" is not on offer from anyone, and a library advertising it would be read with the scepticism Merge applies to Arcade's "8,000 tools but 43 connectors" ([Merge](https://www.merge.dev/blog/composio-vs-arcade)).

### Governance: tiers, owners and loud tests from the first release

Every large catalogue ends up tiered. Airbyte certifies about 71 connectors and labels about 556 as community, with no SLA and a separate archive repository ([Airbyte support levels](https://docs.airbyte.com/integrations/connector-support-levels), [airbytehq/airbyte](https://github.com/airbytehq/airbyte)). The models that lasted give each integration its own package and a named owner, as Terraform's official, partner, community and archived tiers do ([Terraform Registry](https://developer.hashicorp.com/terraform/registry/providers)). Publish tiers and an archive policy with the first release. Make "has live conformance tests in CI" the tier-one boundary, and fail when credentials are missing: OpenDAL's shared behaviour suite skips silently by default and has CI setups for 47 of its 68 services ([OpenDAL behavior tests](https://github.com/apache/opendal/blob/main/core/tests/behavior/README.md), [.github/services](https://github.com/apache/opendal/tree/main/.github/services)). Its tests are selected by declared capability, which transfers well. Its live AWS S3 test names the sponsor who pays for the credentials, which is the one sustainable ownership pattern the research found for live endpoints ([aws_s3 action](https://github.com/apache/opendal/blob/main/.github/services/s3/aws_s3/action.yml)).

Contributed integration code runs in-process with decrypted tokens. In January 2026 at least 10 malicious npm packages posed as n8n community nodes to steal exactly that ([Endor Labs](https://www.endorlabs.com/learn/n8mare-on-auth-street-supply-chain-attack-targets-n8n-ecosystem)). Compile-time opt-in narrows the exposure and does not replace review. The library must be bring-your-own-credentials: Google's API terms state that "developer credentials may not be embedded in open source projects" ([Google APIs Terms](https://developers.google.com/terms)). Publish stub integrations only once they work, since crates.io prohibits crates that exist only to reserve a name ([RFC 3463](https://rust-lang.github.io/rfcs/3463-crates-io-policy-update.html)). Stay permissive. Your MIT licence fits, and `MIT OR Apache-2.0` matches `oauth2` and `octocrab`.

### Naming: `link` and `connector` are both taken

`link` on crates.io is a 2016 crate described as "Now deprecated.", dormant since 2020 and owned by one person, so it would need a voluntary transfer ([link](https://crates.io/crates/link)). It also collides with linker terminology in search. Your current crate name is unavailable too: `connector` was published in April 2026 as a Solana library ([connector](https://crates.io/crates/connector)). On 2026-10-08 the names `linkkit`, `connectors`, `integrations` and `cognis-link` did not exist on crates.io ([linkkit](https://crates.io/crates/linkkit), [cognis-link](https://crates.io/crates/cognis-link)). That check does not guarantee a publish will be accepted, and GitHub and trademark availability were not checked.

Keep `link` as the folder name and pick a crate prefix that reads project-first, as `opendal-service-github` and `rig-mongodb` do. For a library meant to be used without Cognis, a neutral prefix such as `linkkit` (`linkkit-core`, `linkkit-slack`, facade `linkkit`) fits better, with `cognis-link` reserved for the bridge crate. If you intend it as a Cognis companion first, `cognis-link` throughout is the lowest-friction choice, since you already own `cognis` ([cognis](https://crates.io/crates/cognis)). Feature names are permanent API either way, so settle `slack`, `github` and the bundle names before the first publish.

## Conclusion

The question changes shape once the evidence is in. The scarce thing is not a library with many integrations; hosted vendors and MCP already supply breadth, with padded counts. The scarce thing is a permissive, in-process Rust library where the application owns its credentials and gets typed operations, webhooks and sync for the tools it depends on. You already hold a working seed of that, and the Rust ecosystem has no competitor for it. What you would be giving the community is less the 17 integrations than the core they sit on: the provider registry, the token-store trait, the webhook verifier and a conformance suite that makes a contributed integration trustworthy.

The decision that carries risk is scope, not whether to build. Each integration you promise is a standing maintenance and credential cost, and the projects that promised a long tail either restricted their licence to fund it or abandoned it. Extract the core and the integrations your product exercises daily, and publish the tier policy alongside them. Let breadth come from the auth catalogue and the MCP feature until contributors with their own stake show up to own more.
